SC2 — read the max offset / content extent.
SC3 — set the offset.
Tier: `gos run --main-thread`, and every other tier.

(`git archive HEAD` into /tmp/gpui-before):

    cd /tmp/gpui-before
    timeout -k 5 40 gos run --main-thread tests/gui/sc1_scroll_offset.gos

Output (exit 124 — the timeout killed it; the first line is on stderr, which is

  gpui: unknown style tokens: id=panel

Re-run with the runner's build lock cleared first, to be sure the hang was the
probe and not the lock — see "The stale build lock" — and it is the same:

  ########## BEFORE sc1_scroll_offset (locks cleared)
  exit=124
  gpui: unknown style tokens: id=panel

Two failures, and the second is the more specific one.

The loud one is `id=panel`. `id=` is style vocabulary this round added, so at
HEAD `style::is_known` rejects it, `check_style` reports it and the binding draws
an error banner in the window. That is exactly the on-screen banner the strict
regression rule exists to catch, and it is a real observation about the missing
token rather than an assertion about it.

The quiet one is why the probe hangs. `gpui::scroll_offset`,
`gpui::scroll_max_offset` and `gpui::scroll_to` do not exist at HEAD, so frame 1
runs to the end — pushing the container, which is where the banner comes from —
and frame 2's first call is unbound. The binding catches that at its boundary and
draws an error card, but the callback was abandoned *before* it reached
`gpui::animate()`, so no next frame is asked for, the window goes idle, and the
probe never reaches its quit. A hang with one line of stderr, not silence.

This is still the weaker kind of red — the capability is the *reader itself*, so
there is no behaviour to observe before it exists — and `SC4.before.txt` records
the same shape for the same reason.

What the source says, so the absence is not merely asserted: `view.rs` applied
`overflow_x_scroll()`, `overflow_scroll()` and `overflow_y_scroll()` to a
scrolled container and never called `track_scroll`, so the container's
`ScrollHandle` was `None`. gpui keeps the offset either way — a Div with
`overflow = Scroll` falls back to an element-state `Rc` — but a `None` handle is
one no program can reach, and `grep -n "ScrollHandle\|track_scroll\|max_offset"
gpui-binding/src/*.rs` was empty at HEAD. The wheel still scrolled; a scrollbar a
program drew beside it could not follow.

The row this most affects is `02_data_table`, whose scrollbar thumb sits at its
resting position and is inert for exactly this reason (`PORTING.md`, "No
`ScrollHandle`").
