THE HORIZONTAL SCROLL AXIS ON macOS — measured 2026-10-09, in the tree as it stands.

THE CLAIM. "Horizontal scroll is handled by Shift+MouseWheel." It is worth writing down what gpui
actually says, because the answer decides whether the horizontal axis can be driven at all — and
whether a probe that held Shift to reach it would be driving anything.

WHAT GPUI SAYS. `Style::restrict_scroll_to_axis` (`gpui-0.2.2/src/style.rs:166-180`, the crate being
`~/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/gpui-0.2.2`):

    /// Whether scrolling should be restricted to the axis indicated by the mouse wheel.
    ///
    /// This means that:
    /// - The mouse wheel alone will only ever scroll the Y axis.
    /// - Holding `Shift` and using the mouse wheel will scroll the X axis.
    ...
    /// Currently, GPUI operates differently from the web in that it will scroll an element in either
    /// the X or Y axis when scrolling with just the mouse wheel.

So the Shift sentence is not a description of the wheel — it is one half of an **opt-in style
property**, and the other half of that property is the thing that is actually happening when it is
off. It defaults to `false` (`style.rs:741`), and nothing in this binding and nothing in `examples/ui`
ever sets it. The port therefore runs the branch its own Motivation paragraph calls "differently from
the web", and the Shift half is not in force.

WHAT THE CORE DOES ABOUT IT (`elements/div.rs:2413-2444`, all platforms, no backend in sight):

    let restrict_scroll_to_axis = style.restrict_scroll_to_axis;
    ...
    if overflow.x == Overflow::Scroll {
        if !delta.x.is_zero() { delta_x = delta.x; }
        else if !restrict_scroll_to_axis && overflow.y != Overflow::Scroll { delta_x = delta.y; }
    }

A wheel whose only delta is vertical, arriving over an element that scrolls **x and not y**, is spent
as a scroll of that element along x. `modifiers` is never read here, so Shift cannot change this.

WHERE THE SHIFT HALF LIVES. Only in two backends, and each does it to the event *before* the core
sees it: `platform/linux/x11/client.rs:2208` — "When shift is held down, vertical scrolling turns into
horizontal scrolling" — and `platform/windows/events.rs:532,557`. The macOS backend does not:
`platform/mac/events.rs:226` takes `scrollingDeltaX()`/`scrollingDeltaY()` as they come and forwards
`read_modifiers(native_event)` untouched, and the core ignores it for a scroll. **Shift+wheel is a
Windows and X11 convention. On macOS it is a no-op**, in gpui 0.2.2 and in this binding alike.

THE MEASUREMENTS. `examples/16_scrollable.gos` is the two-axis example: an outer `overflow=scroll`
container holding a 2000px-wide green box inside an `overflow=x` one. Driven at the window server's
event tap through `scripts/pointer.sh`, window `1030,470 500x532`, pointer at the green box
(1280,640), one event per row. The landmark is the green box's own 1px border, read out of a
`screencapture` with `magick … txt:-` and not by eye — a border pixel is `0,117,27`, the panel behind
it `239,240,254`, and no judgement is involved.

    gesture                                  before             after
    horizontal wheel, wheel2 = -1600         border at x=33     border at x=466
                                             (the box's left)   (the box's RIGHT)
    vertical wheel, dy = -60                 border at x=33     no border anywhere in that row
                                                                (the left edge has left the clip)
    the same, carrying .maskShift            —                  pixel-identical to the one above
                                                                (`compare -metric AE` = 0)

Read together:

  * **The horizontal axis is real and reachable.** 1600px of wheel drives the container to its end and
    brings the box's far border into view at x=466, so the box is the 2000px its source asks for, the
    clip is about 433px of it, and the offset clamps around 1567. Nothing about horizontal scrolling is
    unreachable here.
  * **A vertical wheel scrolls that box sideways.** Which is `div.rs:2427` above, and is not Shift.
    The same event also moved the enclosing vertical container by the same 60px, since both handlers
    are offered a bubble-phase scroll (`elements/div.rs:2418`'s listener and the outer container's) —
    a vertical wheel over a horizontal box moves both, and a probe must expect that.
  * **Shift changes nothing.** Same gesture, same window, same frame: `AE = 0`. A probe that held
    Shift to reach the horizontal axis would be holding a key gpui does not read on this platform.

WHAT THIS CORRECTS. In the round that first drove example 16 with a wheel, readings were taken at
(1280,752) and showed the content moving vertically; that point is over the *outer* container, which
scrolls both ways, so a vertical wheel there can only move it vertically. They said nothing about the
horizontal axis and were reported as though they had. The point that matters is the one over the
`overflow=x` container, and the numbers above are from there.

WHAT IT DOES NOT CHANGE. This is not a port deviation and the pairs are unaffected. The port and
`tools/upstream/examples/scrollable.rs` are the same gpui 0.2.2 on the same machine, so the axis
behaves the same in both, and `census.tsv`'s single row for `16_scrollable` (the `hsla` alpha bullet)
stands unaltered.

WHAT A PROBE WOULD DO. Not hold Shift. Either drive the horizontal axis of the wheel directly —
`scripts/pointer.sh hscroll <x> <y> <dx>`, which posts the same `CGEvent` with the second wheel axis
set, and is the axis a trackpad's two-finger sideways swipe produces — or drive the vertical one at a
point over the x-only container and read the container's own offset back, `gpui::scroll_offset`
(SC1) being the reader.
