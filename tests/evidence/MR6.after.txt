What changed, all in `gpui-binding/src/`:

  * `view.rs` — `asset_root()`, the directory a program declared, and `asset_path(name)`, the one
    resolver: an empty name and an absolute path come back unchanged, the declared root is tried
    first, and **a miss falls back to the name as it was given** — which is what keeps a program
    that declares no root behaving exactly as it did. `Kind::Image` and `Kind::Icon` now resolve
    through it, so `gpui::image` and `gpui::icon` and `gpui::asset_path` cannot drift apart.
  * `lib.rs` — `gpui::asset_root(dir)` to declare one (per window, `""` by default) and
    `gpui::asset_path(name)` to read the same resolution for a file a program opens itself.
  * `README.md` — the `ui::image` / `ui::icon` row now says where a path resolves.

**The row as a whole is not closed, and the entry says which clause is which.** `MR6` is
`tested` for the path-resolution clause, which is the defect the register named. Its
`ui::editor` multi-line clause is **DW1's row** and remains `todo` — a completed row cannot be
closed out by an unfinished one — and its `ui::scroll` clause needed nothing: a style with
`id=panel` in it is already what `gpui::scroll_offset` and its three neighbours read.

Residual doubt. **The element arms are read, not measured**: `Kind::Image` and `Kind::Icon` now
call `asset_path`, and that is the half a program uses, but seeing it needs a window — which this
machine's owner has forbidden. What *is* checked is the resolution they share. The two guards
named in `MR6.before.txt` are unobservable by construction. A root is a *per-window* setting while
assets are usually per application, so a program with two windows must declare it in both — the
convenience of a process-wide root would be a different decision, and this one is deliberate (it
is the same choice every other per-window registry here makes). And resolving runs a `stat` per
element per frame for a relative path, which for a list of a thousand images is a thousand
`stat`s a frame: a cache would be the next thing, and nothing here needs one yet.
