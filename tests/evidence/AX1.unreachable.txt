AX1 — program-authored `impl Render`, `impl Element`, `impl RenderOnce`: UNREACHABLE.

Two independent proofs, and the compile error is the easy one to read. A Gosamer
program that tries to implement a trait it does not itself declare:

    $ cat tests/gui/zz_impl_probe.gos
    use gpui

    struct Thing { n: i64 }

    impl gpui::Render for Thing {
        fn render(self) -> i64 { self.n }
    }

    fn main() { println("hi") }

    $ env -u GOSSAMER_IN_RUNNER gos check tests/gui/zz_impl_probe.gos
    error[GT0070]: unknown trait `Render` in `impl Render for Thing`
      --> tests/gui/zz_impl_probe.gos:7:1
       |
     7 | impl gpui::Render for Thing {
       | ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
      = note: declare the trait, fix the spelling, or write `impl <type>` with no trait name
      = help: nothing declares `Render`, so the block's methods are inherent methods on
              `Thing` under a header that promises a contract

    error: check failed with 1 diagnostic(s)

(That probe was removed immediately; a file that does not compile does not belong in
`tests/gui/`, where `scripts/probes.sh` sweeps every `*.gos`.)

An `impl` block is a *declaration in the program's own source*, and the ABI has no shape
for one: a binding item is a monomorphic, module-level free function with `Copy` values
in and out. The rule, quoted from the toolchain:

    $ sed -n '292p;294p' $GOSSAMER_ROOT/crates/gossamer-binding/src/native.rs
        type Input: Copy;
        type Output: Copy + Default;
    $ grep -rn "no generics, no traits" $GOSSAMER_ROOT/crates/gossamer-binding/src/
    .../src/types.rs:6://! Gossamer's full type system - no generics, no traits - so the

Those are R1 and R2 in this register's own list. R1 is why `Entity`, `Subscription` and
`dyn Trait` cannot cross either. R3 — the ABI is inert data plus `i64`/`u64` handles, and
a trait *implementation* is never a value — is what makes this structural rather than a
matter of effort: even with a `Copy` handle, there is no call the host could make later.

And "later" is the whole point of the row. `Render::render`, `Element::prepaint` and
`RenderOnce::render` are called by **gpui's own loop**, in a frame the host is building,
after every binding function has returned. A binding-owned closure cannot be invoked
from there without the application-lifetime trait registry the register's obstacle
column names — and even that registry would need the two rules above relaxed to carry a
vtable.

The toolchain change that would close it: a `dyn Trait` with a `'static` vtable that can
cross the ABI, or an application-lifetime registry keyed by handle whose entries the
host may call arbitrarily later. Neither exists, and the register says to record this
rather than stall on it.

What a program can do instead, and it is not a substitute: `gpui::draw(painter, phase,
style)` plus the path pool are a *fixed* painter, and `ui::draw` is how a program paints
inside a frame it does not own. That is DW10's business, not this row's.
