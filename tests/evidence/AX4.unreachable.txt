AX4 — screen capture to a file: UNREACHABLE, and the row's own instruction ("verify before
recording `UNREACHABLE`") is what turned it over. It was verified, and the verification went
the other way twice: this build has no capture in it, and the capture that a build *with* one
would perform cannot hand a single pixel to the crate that asked for it.

--- 1. This build has no capture in it at all

gpui compiles the whole feature out unless one Cargo feature is named:

    $ grep -n "screen-capture" ~/.cargo/registry/src/*/gpui-0.2.2/Cargo.toml
    .../Cargo.toml:55:screen-capture = ["scap"]

    $ grep -n "^gpui = " gpui-binding/Cargo.toml
    39:gpui = { version = "0.2.2", features = ["runtime_shaders"] }
    42:gpui = { version = "0.2.2", default-features = false, features = ["x11"] }

Neither line names it, on either platform. So `App::is_screen_capture_supported()`
(`src/app.rs:1009`) and `App::screen_capture_sources()` (`:1014`) both forward to the
`not(feature)` defaults of `PlatformWindow`, and those defaults are literals:

    $ grep -n "fn is_screen_capture_supported\|fn screen_capture_sources\|compiled without the screen-capture" -A 2 \
        ~/.cargo/registry/src/*/gpui-0.2.2/src/platform.rs

`is_screen_capture_supported()` is `false` and the sources call answers one error with one
sentence in it. That is the whole of what screen capture is, in a binding built the way this
one is built.

**That alone would not be an unreachability, and this is the part the first verification
missed: a feature is a choice, not a wall.** The binding could add `screen-capture` and get a
build that compiles `scap` in. The wall is what happens next.

--- 2. With the feature on, no pixel can leave the callback

The API is this, and the shape of it is the problem:

    $ grep -n "pub trait ScreenCapture\|fn metadata(&self)\|fn stream(\|pub struct ScreenCaptureFrame" \
        ~/.cargo/registry/src/*/gpui-0.2.2/src/platform.rs
    316:pub trait ScreenCaptureSource {
    318:    fn metadata(&self) -> Result<SourceMetadata>;
    322:    fn stream(
    330:pub trait ScreenCaptureStream {
    332:    fn metadata(&self) -> Result<SourceMetadata>;
    336:pub struct ScreenCaptureFrame(pub PlatformScreenCaptureFrame);

A frame reaches a caller in exactly one way — as the argument of `frame_callback` — and the
only way into that argument is its single field. That field is `pub`. Its *type* is not:

    $ grep -n "PlatformScreenCaptureFrame = " ~/.cargo/registry/src/*/gpui-0.2.2/src/platform/linux.rs \
                                                 ~/.cargo/registry/src/*/gpui-0.2.2/src/platform/mac.rs
    .../platform/mac.rs:59:pub(crate) type PlatformScreenCaptureFrame = CVImageBuffer;
    .../platform/linux.rs:27:pub(crate) type PlatformScreenCaptureFrame = scap::frame::Frame;
    .../platform/linux.rs:29:pub(crate) type PlatformScreenCaptureFrame = ();

on both platforms, and there is no method anywhere that reaches a frame's contents:

    $ grep -rn "impl ScreenCaptureFrame" ~/.cargo/registry/src/*/gpui-0.2.2/src
    (no output)

A `pub` field on a `pub` struct whose type is `pub(crate)` looks readable and is not. Measured,
with the smallest pair of crates that has that shape:

    $ cat a.rs
    pub(crate) struct PlatformFrame { pub pixels: u32 }
    pub struct Frame(pub PlatformFrame);
    pub fn make() -> Frame { Frame(PlatformFrame { pixels: 7 }) }

    $ cat b.rs
    fn main() {
        let f = a::make();
        let inner = f.0;
        let p = inner.pixels;
        println!("read {p}");
    }

    $ rustc --edition 2021 --crate-type lib --crate-name a a.rs -o liba.rlib
    warning: type `PlatformFrame` is more private than the item `Frame::0`
      --> a.rs:2:18
       |
     2 | pub struct Frame(pub PlatformFrame);
       |                  ^^^^^^^^^^^^^^^^^ field `Frame::0` is reachable at visibility `pub`
       |
    note: but type `PlatformFrame` is only usable at visibility `pub(crate)`
      = note: `#[warn(private_interfaces)]` on by default

    $ rustc --edition 2021 --crate-type bin --crate-name b b.rs --extern a=liba.rlib
    error: type `a::PlatformFrame` is private
      --> b.rs:3:17
       |
     3 |     let inner = f.0;
       |                 ^^^ private type

    error: type `a::PlatformFrame` is private
      --> b.rs:4:13
       |
     4 |     let p = inner.pixels;
       |             ^^^^^ private type

The defining crate gets a warning and compiles; the crate outside gets an error on the field
access itself, before anything could be done with the value. `gpui` is the defining crate and
the binding is the outside one, exactly as any program is: **the binding is not privileged
here.** Nothing about the binding's position inside the process reaches past a crate boundary
that the compiler enforces with an error.

What *is* reachable is the enumeration, and it is worth saying so rather than leaving the row
looking empty: `SourceMetadata` is `pub` with four `pub` fields,

    $ grep -n "pub struct SourceMetadata\|    pub id\|    pub label\|    pub is_main\|    pub resolution" \
        ~/.cargo/registry/src/*/gpui-0.2.2/src/platform.rs
    304:pub struct SourceMetadata {
    306:    pub id: u64,
    308:    pub label: Option<SharedString>,
    310:    pub is_main: Option<bool>,
    312:    pub resolution: Size<DevicePixels>,

and all three `impl ScreenCaptureStream` (`platform/scap_screen_capture.rs:252`,
`platform/mac/screen_capture.rs:157`, `platform/test/platform.rs:74`) implement `metadata()`
and nothing else. A program could be told which displays exist and how large they are. It
could never be handed the picture.

--- 3. And route D does not help

Route D is "expressible only as a Rust-side widget inside the binding", and it exists for
things a program writes *into a frame the binding owns*. A capture is not in a frame: it
arrives on gpui's own thread, through a callback whose argument type the binding cannot name,
and the widget that would draw it would have nothing to draw. Route D puts Rust on the inside
of the ABI; it does not put the binding on the inside of gpui.

--- 4. One route exists that is not this row

The binding could depend on `scap` (the crates.io package `zed-scap`, which gpui's own Linux
backend uses) and capture the screen without gpui at all. That is a second screen-capture
library wired into the binding, not gpui's capability, and the register's question is what a
program can do **through the binding as gpui's surface**. It is written down here so that the
route is dismissed rather than overlooked.

**What would close AX4, upstream:** any accessor on `ScreenCaptureFrame` — one `pub fn` giving
the pixels, the size, or an image — or a `ScreenCaptureSource` that answers something other
than metadata. With one of those, and the `screen-capture` feature turned on in
`gpui-binding/Cargo.toml`, the row is a binding change and a probe.
