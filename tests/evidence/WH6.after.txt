Output, identical on all five tiers (`check` prints `check: ok (1 items typed)`; each of
the other four exits 0 with no stderr but the toolchain duplicate-symbol link warnings
every build in this project prints):

    OK WH6 outer 320x232 and inner 320x232 while windowed; a resize to 430x310 raised a bounds event and the window now reports 430x342

What the probe does, in order:

  * at frame 2, asserts that the window reports an inner size at all, that it is not
    larger than the outer one, that a window opened windowed says `"windowed"`, and that
    it reports no restore size — then asks to observe its bounds;
  * at frame 3, drains the event the observer raises as it installs itself (gpui's
    `observe_window_bounds` runs its callback once immediately), so that the event the
    verdict waits for can only be the resize's, and resizes the window to 430x310;
  * from frame 4, requires that event to arrive and that the window report the new
    geometry.

What is new:

  * `gpui-binding/src/view.rs` — `begin_frame` captures the window's content rectangle
    (`Window::inner_window_bounds`) and what `Window::window_bounds` says about its
    state and restore size, beside the outer rectangle it already captured.
  * `gpui-binding/src/lib.rs` — `window_field` gains `inner_x`, `inner_y`, `inner_w`,
    `inner_h`, `restore_w` and `restore_h`; `window_bounds_state()` answers
    `"windowed"`, `"maximized"` or `"fullscreen"`; and `observe_window_bounds(id)`
    raises an event whose payload is the new `"x,y,w,h"`.
  * `gpui-binding/src/app.rs` and `store.rs` — the request and its installation through
    `Context::observe_window_bounds`, the same retained-callback shape CL1 uses for
    `on_window_should_close`. The callback runs under `window::with`, so the event lands
    in the right window's queue.

What is *not* verified here, and why:

  * **Inner and outer are the same numbers on this platform** — 320x232 both — because
    macOS implements no inset for its content rect: the `PlatformWindow` trait's default
    `inner_window_bounds` returns `window_bounds` (`platform.rs:531`) and the macOS
    backend does not override it. The check is therefore `inner <= outer` and
    `inner > 0`, which is platform-neutral, rather than "they differ"; that they differ
    on Windows, Wayland or X11 is read from the trait, not measured.
  * **`restore_w`/`restore_h` are checked only for a windowed window**, where they are
    zero. For a maximized or fullscreen window they carry the `WindowBounds` variant's
    own restore size, and reading that on this machine means either going fullscreen —
    which this run does not do to a machine someone is sitting at, see `WH2.after.txt` —
    or zooming, which macOS reports as `WindowBounds::Windowed` because it has no
    maximized state of its own. So the state half of this row is exercised only in its
    windowed case.
  * The 32-pixel difference between what the window is asked for and what it reports —
    430x310 requested, 430x342 reported — is the titlebar, and it is why the assertions
    use ranges rather than equalities.
