What changed, all in `gpui-binding/src/`:

  * `app.rs` — `ProgramKey`, one action type this binding owns, derived through
    gpui's own `Action` macro with `no_json, no_register` so it needs no new
    dependency. It carries the program's event name, and gpui dispatches an action
    by type and hands the handler the value, so one type serves every binding.
    `install_program_actions` wires it once with `cx.on_action` and raises the name
    in the window that bound it, through `KEYMAP_OWNER` — the `MENU_OWNER` shape,
    for the same cross-window reason. `keymap_plan` is the one parse, shared by the
    request that binds and the reader a program calls; `keymap_spec` answers what
    was bound, in order; `bind_keys_spec` applies a spec, refusing a stroke gpui
    cannot parse with `"~keybind.bad|<stroke>"` rather than letting
    `KeyBinding::new` panic.
  * `store.rs` — `Request::BindKeys { spec }`.
  * `lib.rs` — `gpui::bind_keys(spec)`, `gpui::keymap()`, `gpui::keymap_plan(spec)`,
    each documented; `README.md` gains the three rows.
  * The tests: `tests/km1_keymap_test.gos` (four headless cases for the parse) and
    `tests/gui/km1_keymap.gos` (bind three, fire three, in order, in the window that
    asked).

Residual doubt. The bindings are **global**, not focus-scoped: one application
keymap answers for every window, and a stroke bound by window A is matched in
window B too — the event is routed to the window that bound it, so the program sees
it once and in the right place, but the *match* is not scoped. That is exactly
row **KM2** ("key contexts, so bindings are focus-scoped"), which is the next row in
this block. Also unverified: a real key press rather than `gpui::send_key` — the
two paths are the same dispatch, but the check drives the synthetic one, which is
the strongest instrument this binding has (nothing can synthesize a pointer or a
release; see `## Unreachable`).
