02_data_table — the regression, re-verified with the window-only capture
Tier: check (clean), run (interpreter, exit 124 under a 20s bound as a GUI example
that never quits); captured with `screencapture -x -o -l <window number>`.

THE CLAIM. Round 81–82 found this example drawing its rows **empty** — 42 tinted
bars with no text — while passing every silence check, and commit 6251b01 fixed
the cause (a `uniform_list` rendering its rows outside the frame's window, so every
child handle missed the arena). This is the re-check, and it is done the three ways
the round made possible.

  1. **With `GOSSAMER_NOTED_ERRORS=1` set, the example prints nothing.** That is
     the channel doing its job: if any child handle still missed, or any style
     token were unknown, the binding would note it and the note would be on stderr.

         $ DSH_ALLOW_WINDOWS=1 TIER_TIMEOUT=20 ./scripts/tiers.sh examples/02_data_table.gos check run
         === check ===
         check: ok (46 items typed)

         === run (interpreter) (exit 124) ===

         === tiers exit=0 ===

     An empty transcript under that variable is the strongest single statement
     available: silence from a program that runs with its own error channel turned
     on is not the silence that hid this fault.

  2. **The rows have text in them.** `EX02.after.png` sits beside this file and was
     taken with `screencapture -x -o -l <number>` — **the window's own pixels, with
     the desktop left out**, which is what makes this evidence stable when the
     person at the machine switches workspace or opens something over it. It shows
     41 body rows, ids 0 through 40, every column filled — SYMBOL, NAME, LAST DONE,
     PREV, CLOSE, OPEN, LOW, HIGH, TTM, MARKET CAP, FLOAT CAP, TURNOVER, VOLUME,
     TURNOVER — with the green/red colouring intact.

  3. **The scrollbar renders, and it is measured rather than eyeballed.** Scanning
     the capture for the thumb's own colour (rgb(184,184,184)):

         thumb pixels 768   x 1251..1258   y 113..210
         -> 8 px wide, 98 px tall, 21–28 px in from the right edge,
            starting exactly at the top of the body

     768 = 8 x 96, so it is a solid rounded rectangle and not a fringe. That is
     the example's own scrollbar — `examples/02_data_table.gos:368` draws it, and
     its header says "a grey scrollbar thumb over the body, 8x100 with a hover
     refinement", so 8x~100 is the design and the thumb does not resize with the
     10,000 items. It sits at the top because the list is at offset 0.

WHAT "visible range: 0..42" MEANS, because this was asked and it is not a port
bug. 41 rows are on screen (0..40) and the header says 0..42. The label prints the
range gpui hands to the row builder:

    examples/02_data_table.gos:407   let heading = f"Total {TOTAL_ITEMS} items, visible range: {range}"

and upstream prints the same slot from the same source —

    tools/upstream/examples/data_table.rs:385   "Total {} items, visible range: {:?}", self.visible_range
    tools/upstream/examples/data_table.rs:430   this.visible_range = range.clone();   // the uniform_list processor

so the extra rows are gpui's own overscan (the prefetch a `uniform_list` does
beyond the viewport) reported verbatim, and upstream shows the same figure. The
port's header comment at `examples/02_data_table.gos:46` says this, including that
in both versions the header is one frame behind. Nothing here is wrong, and the
port reproduces upstream exactly — which is the standard this example is held to.

WHAT IS NOT CLAIMED: that the table has been compared side by side with upstream's
own binary this round. `EX02_ROWS.upstream.png` in this directory is that
comparison from round 82; this page is the re-verification of the port after the
fix, not a second comparison.
