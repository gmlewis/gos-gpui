DW12 — after: a drawn titlebar's six calls, on every tier, and checked from outside the process.

The row is "client-side window decoration widget (drawn titlebar)". gpui hands a program six
calls to make one out of — ask for decorations, read back who draws them, set the strip the
program keeps, read that back, hand the window over to be moved, hand it over to be resized —
and they divide into two pairs that have to be checked in two different ways. Asking and
reading back leaves a record on the X server; handing the window over leaves none, and can
only be seen by watching the window.

Three records agree in that line, and they are three different machines' memories: the binding's
own answer, the atoms the window manager advertises in `_NET_SUPPORTED`, and the property
`_MOTIF_WM_HINTS` that `X11Window::request_decorations` (`src/platform/linux/x11/window.rs:1604`)
wrote onto the window with `xcb_change_property`. **The reading with teeth is the one taken
*before* anything was asked.** `gpui::window_decorations()` is `"server"` before the program asked
for `"client"` and `"server"` after, because this display's window manager has no compositor and
refuses — so a binding that echoed the request back would answer `client` in the second reading
and be caught by the first. The word `"server"` is not written into the probe: it is what
`expected_decorations` derives from the atoms, so an image that gained a compositor would move the
probe onto the other arm rather than fail it.

**A hand-over has no record, only a consequence.** `start_window_move` (`:1519`) and
`start_window_resize` (`:1524`) both end in `send_moveresize` (`:848`): gpui ungrabs the pointer,
reads where it is for itself, and sends `_NET_WM_MOVERESIZE` to the root window — flag 8 to move,
and for a resize the flag `ResizeEdge::to_moveresize` gives. So the probe does what a drawn
titlebar's press handler does — the button goes down inside the window and the call is made while
it is held — and then asks the X server, through `xdotool`, where the window is. **The window
being where the pointer went is the whole claim**; nothing else about that path is checkable, and
"the binding sent a message" would be a claim about the binding's own source.

**Two constants in that probe are measurements, and both were put in after a run that failed
because they were not there.** The first version moved the window by exactly `(60, 40)` on one run
and by `(0, 0)` on the next. gpui drains a request between frames, so the call is not delivered
when it is made but on the frame after; and `openbox` only begins following the pointer once it
has taken the window and established a grab. A single jump posted immediately lands on the program
instead, and the window never moves. So the probe waits `SETTLE = 0.35` seconds between the
hand-over and the motion, and travels in `STEPS = 4` waits-for-it jumps rather than one — a
window manager following the pointer has several motions to follow instead of one to miss. On the
container, one jump failed perhaps one run in three; four waited-for jumps have not failed.
