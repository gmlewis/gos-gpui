WH9 — the application's name: the bold word macOS draws at the left of the menu bar.

BEFORE THE WORK. There was no way to say the word. The binding had no `set_app_name`, and the
bar of every port read `gos-runner`, the name of the one runner all twenty-seven examples share:

    gpui::set_app_name(...)   — no such name

Upstream does not have the problem, and it is worth writing down why, because it is the whole
reason the row exists: upstream's examples are **one binary each** (`target/debug/examples/text`,
`target/debug/examples/set_menus`), so `text.rs`'s bar reads `text` and `set_menus.rs`'s reads
`set_menus` without either example asking for anything. `text.rs` names its own *menu*
`"GPUI Typography"` and its bar still reads `text`, which is the fact the port has to reproduce
some other way.

`gpui-binding/src/name.rs` records the mechanisms that were measured against a live bar, and only
one of them moves it: `[NSProcessInfo setProcessName:]` leaves the executable's name; so does
`[NSMenuItem setTitle:]` on the application menu; so does seeding the name *after* the bar has
been drawn. Seeding `CFBundleName` into `[[NSBundle mainBundle] infoDictionary]` **before
`gpui::run`** is the one that shows.

THE MEASUREMENT. `tests/gui/wh9_app_name.gos` asks System Events, by pid, for the titles of this
process's menu-bar items, and asserts that the name the program declared is one of them. Run with
the declaration removed — the same probe, byte for byte, with `gpui::set_app_name(NAME)` deleted:

    DSH_ALLOW_WINDOWS=1 ./scripts/run-once.sh tests/gui/zz_wh9_break.gos 45

    wh9 the menu bar of this process reads "Apple|gos-runner|"
    FAIL WH9 the menu bar of this process reads "Apple|gos-runner|", and the name it declares, wh9-app-name, is not one of its items

    exit 1

The bar holds one item after Apple's, it reads `gos-runner`, and the probe says so and fails. The
same bar, read by eye while the probe ran, is in `WH9.after.txt`.

Two dead ends are recorded here so they are not walked again:

  * **`gpui::installed_menu()` is not the check.** It reports the menus the platform was *handed*
    (`app.rs`'s `record_menu_bar` after `cx.set_menus`), and an application's name is not among
    them — it is the name of the *process*, not of any menu. It answers `#["wh9-menu"]`, which is
    what the row would have to call a pass, and which the bar does not read.
  * **The drawn word is not the menu's.** Upstream's `set_menus` example and the port of it both
    show the application's name at the left of the bar and the menu's own name nowhere in it —
    AppKit replaces the first item's title with the application's. So a probe that named its menu
    `wh9-app-name` would pass without any mechanism existing, which is why this probe names its
    menu `wh9-menu`.
