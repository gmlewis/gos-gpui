MR5 — focus: a `focusable`-only element must be visible to `is_focused`, and the tokens must work on a button.

AFTER THE WORK. Two questions, two answers, and the row is one of them.

    $ DSH_ALLOW_WINDOWS=1 ./scripts/run-once tests/gui/mr5_focus.gos 45
    MR5 step 1: neither button is focused before the tab order moves
    MR5 after 1 focus_next: "" holds focus
    ... eight presses, every one "" ...
    MR5 after gpui::focus("mr5.a"): gpui::focused() says "mr5.a"
    MR5 step 4: a handle of this crate's own can be focused directly, and is_focused reports it
    OK MR5 the focus readers work on a focusable-only button; the tab order is a separate question

**The row is the last two lines.** A button whose style says only `focusable=true` — no `input`, no `editor`,
nothing this crate built a handle for before round 60 — is now focused by name and **reported** by
`gpui::is_focused`. That is "the focus tokens work on a button" and "`is_focused` observes a focusable-only
element", which is what the row asks for.

**The first eight lines are not this row.** `gpui::focus_next` reached no element at all — not the buttons,
not anything — in eleven presses across two runs. Handles are tracked (div.rs:616-620 sets both the flag and
the tracked handle) and inserted at paint (div.rs:1816), and `focus_enabled` is never cleared, yet the walk
finds nothing. That is a defect about the tab order, and it is recorded here rather than folded into this
row's verdict, because MR5's clauses do not depend on it: a program can focus and observe focus without a
working tab order, and now can do both.

What changed, all in `gpui-binding/src/`: `view.rs` — the `focusable` token tracks a handle of this crate's
own (`track_focus(&focus_for(win, id, cx))`), alongside gpui's flag; `handle_for` looks one up without
creating it; `focused()` reports which id holds focus. `lib.rs` — `gpui::focused()` and `gpui::focus(id)`,
with `is_focused`'s doc corrected, since it used to say a `focusable` element could never be seen here.
`README.md` documents both readers.

Residual doubt.

  * **Tiers: `check` and `run`.** The compiled tiers need one more run each; this probe asks nobody for
    anything, so they are cheap, but they were left for a pass the owner can watch rather than spent
    unannounced — as four unannounced windows were spent in round 69.
  * **The tab order does not work**, so `tabstop=` and `tabindex=` are *parsed* (MR3 covers that) and their
    ordering is unverified — this probe could not walk a single step. The row's tokens are therefore proven
    for `focusable` and `focus=`, and not for the two that order things.
  * `focus=`'s *appearance* — whether the refinement actually lights the element up — is unverified: that is
    paint, and there is no Screen Recording permission here.
  * `gpui::focus(id)` on an id with no handle does nothing and says nothing; a program learns that from
    `gpui::focused()` on the next frame, not from a return value.
  * When more than one handle reports focus at once, `gpui::focused()` answers the lexicographically first,
    because a set has no order.
