MR5 — focus: the probe's transcripts, and a finding the row cannot explain away.

**This row is NOT finished**, and this file is the reason a reader can see why without re-running it.

The probe (`tests/gui/mr5_focus.gos`) walks the tab order with `gpui::focus_next` and reads
`gpui::is_focused` after each step. Two versions ran, in two windows:

    # first version — assumed the first focus_next reaches the first button
    MR5 step 1: neither button is focused before the tab order moves
    FAIL MR5 focus_next did not reach the first focusable button (first=false, second=false)

    # second version — walks, and reports whatever holds focus
    MR5 step 1: neither button is focused before the tab order moves
    MR5 after 1 focus_next: nothing has focus
    ... eight presses, every one "nothing has focus" ...
    FAIL MR5 the tab order never reached both buttons in order (first=false, second=false)

**What that means, and what it does not.** The second transcript is the informative one: eight presses
moved focus to *nothing at all* — not to the buttons, and not even to the `~root` handle that
`gpui::is_focused`'s own doc names as one of the elements this binding can see. So the failure is not
about the two buttons and not explained by MR5's change: **`gpui::focus_next` appears to find an empty
tab order in this binding.**

The windowless reading that followed narrowed it to one place and no further:

  * `Window::focus_next` returns early unless `focus_enabled` (`window.rs:1414`), and that flag is
    cleared **only** by `Window::disable_focus()` (`window.rs:1406-1410`) — which nothing in gpui calls.
    So the guard is not the cause.
  * `Window::focus_next` then asks `rendered_frame.tab_stops.next(self.focus.as_ref())`
    (`window.rs:1418`), and `TabStopMap::next(None)` takes `self.order.first()` — so an empty answer
    means an **empty tab map**.
  * A tracked focus handle *is* inserted unconditionally at paint time — `elements/div.rs:1816`:
    `if let Some(focus_handle) = &self.tracked_focus_handle { window.next_frame.tab_stops.insert(focus_handle); }`
    — so the buttons, which are `track_focus`ed by `apply_focus_order`, ought to be in it.

Those three facts do not agree with the transcript, and closing the gap needs instrumentation *inside a
window* — which costs the owner a window per attempt. Four windows were spent on this row (the two
promised probes, one retry after the `focusable()` fix, and the walk), and the round stopped rather than
spend a fifth.

**Where it stands:** `MR5` is `implemented`, not `tested`. Its code change is minimal and faithful —
`focusable` now sets gpui's flag **and** tracks the binding's own handle, so the element's focus is the
one `is_focused` reads; round 69 restored the flag after round 65 removed it by mistake, which the first
transcript caught. What is unverified is whether the tab order works at all in this binding, and that
question is larger than this row.
