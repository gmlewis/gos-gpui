Weak red, same shape as `WH1.before.txt`: `gpui::window_option` is the probe's
first call on frame 2, the callback is abandoned above the `animate()` that would
ask for another frame, and the window goes idle.

Two things the row is right about, read from the source before the work:

  * `WindowBounds::Maximized` and `WindowBounds::Fullscreen` are **not** honored at
    open on this platform. `WindowBounds::get_bounds()` returns the inner bounds
    for all three variants (`gpui-0.2.2/src/platform.rs:1207-1213`), so the macOS
    creation path opens a *windowed* window of the given size; the state is only
    acted on later, in `Window::set_bounds` (`window.rs:1002-1003`), which calls
    `platform_window.toggle_fullscreen()` or `platform_window.zoom()`. A program
    asking to open maximized therefore has to be zoomed *after* it exists.
  * Nothing in the binding could make that call. `Window::zoom_window`
    (`window.rs:1741`) and `Window::toggle_fullscreen` (`window.rs:4122`) were both
    unexposed, and so were `Window::is_maximized` (`window.rs:1450`) and
    `Window::is_fullscreen` (`window.rs:1698`) — so the state could not be read
    back either.

The break that isolates this row's mechanism — `options::take_start` answering `None`
for every window, so one that asked to open maximized is never zoomed:

    timeout -k 5 60 gos run --main-thread tests/gui/wh2_window_state.gos
    exit 124, no output, after 60 seconds

Not the pretty red, and the reason is a property of the environment rather than of
the binding: the window it opens is windowed, the desktop occludes it, and an
occluded window stops being painted — measured here, frames stopped around frame 40
with the process still alive — so the probe's own four-second deadline, which only a
frame callback can look at, is never reached. The check does fail (the tier harness
reports `exit 124`); it just cannot say why. Recorded in the row's residual doubt.

Restored immediately, and the restore re-checked by the `check` tier below.
