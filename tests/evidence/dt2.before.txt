Round 98 — `02_data_table`'s drag bullet, and the two controls it was deleted against.

Command: ./scripts/gosbox.sh run tests/gui/dt2_thumb_drag.gos 40

At HEAD, `examples/02_data_table.gos` carried this paragraph and this deviation:

    // One of the binding's limits meets this example — a drag is tracked only while
    // the pointer is over the element the handler is on — so read the deviations
    // before comparing the two windows.
    //
    // Deviations:
    //
    //   * The drag is element-scoped, where upstream captures the pointer
    //     window-wide. Upstream registers `window.on_mouse_event` handlers so a drag
    //     keeps tracking after the pointer leaves the thumb; `gpui::on_mouse`
    //     reports only while the pointer is over the element it was attached to. The
    //     thumb therefore listens through a 16-pixel strip at the right edge rather
    //     than on the 8x100 thumb itself: a vertical drag stays inside the strip for
    //     its whole length, so the drag works, and the strip is narrow enough that
    //     the wheel over the body still reaches the list. A drag that leaves the
    //     strip sideways stops, which is the difference from upstream.

Both halves of that are now closed and the bullet is gone: `gpui::on_mouse_window` (round 96,
register row `DD4`) is upstream's own instrument and keeps the drag alive past the thumb, and
the mapping is upstream's expression transcribed term for term. This file records the two runs
that show what each half looked like while it was still true.

The gesture is one press 5 px below the thumb's top, one move to a point 250 px below the
thumb's top — 150 px below the thumb's *bottom*, so an event the thumb's own hitbox could not
hear — and a release at the same point, posted by `xdotool` through XTEST against the
container's X server.

The numbers are the same in both runs below and in `tests/evidence/dt2.after.txt`: the thumb
reads back as `8.0x100.0` at `296.0,12.0`, the list's viewport as `h=400.0` at `y=8.0`, its
maximum offset as `219600.0` (= `10_000 * 22.0 - 400`), the press grabs `grab=-3.00`, and the
move the drag is carried by lands at window `y=262.0`.

--------------------------------------------------------------------------------
1. The tracking half: the element-level listener the example carried
--------------------------------------------------------------------------------
`WINDOW_LEVEL: false` registers the same tree, the same gesture and the same rule with
`gpui::on_mouse` instead of `gpui::on_mouse_window` — which is the call the example used. gpui
gates an element listener on its hitbox being hovered
(`gpui-0.2.2/src/elements/div.rs:128`, `:147`), so the press is heard — it lands on the thumb —
and then nothing is. The move happens where the thumb is not, and so does the release.

FAIL   tests/gui/dt2_thumb_drag.gos: exited 0 — no verdict
       FAIL DT2 no move carried the drag: the pointer went 250 px below the thumb's top and the list never moved (offset 0.0)
       FAIL DT2 the thumb heard 0 release(s), not 1: a release outside the thumb reached nobody
       ok     DT2 the drag held the point it grabbed: press 5 px into the thumb, dragged 245 px lower, and the list settled at 0.0 of 219600.0 -- exactly what upstream's mapping asks for
       FAIL DT2 the rule the example carried before round 98 asks for 0.0 too, so this check cannot tell the two rules apart
       note DT2 thumb at 296.0,12.0 8.0x100.0; list at y=8.0 h=400.0 max=219600.0; grab=-3.00; move at y=0.0; 0 move(s) drove it

The offset never leaves 0.0, so the drag dies the instant the pointer leaves the thumb — the
deviation's first clause, reproduced from the probe alone. The `downs` line is absent because
the press *was* heard, once: that is the whole shape of the element-scoped limit, and it is why
the probe checks the move and the release rather than the press. (The fourth line is vacuous
here for the same reason the fifth one fails: with nothing heard there is no move, so the two
rules have nothing to disagree about. That is why the `moves < 1` check sits *above* the
arithmetic rather than relying on the arithmetic.)

--------------------------------------------------------------------------------
2. The mapping half: the rule the example carried
--------------------------------------------------------------------------------
`RULE: 0` applies the rule the example carried before this round — the pointer's own place in
the viewport, `clamp01((py - thumb_y) / h) * max`, with nothing held — to the very same move.
The window-level listener is back in place, so the move *is* heard; it is the arithmetic that
is the one that was there.

FAIL   tests/gui/dt2_thumb_drag.gos: exited 0 — no verdict
       FAIL DT2 the drag asked the list for 137801.2 and it settled at 137252.2: -549.0 px out
       ok     DT2 the rule the example carried before round 98 would have asked for 137252.2 instead, 549.0 px away, so this check tells the two rules apart
       note DT2 thumb at 296.0,12.0 8.0x100.0; list at y=8.0 h=400.0 max=219600.0; grab=-3.00; move at y=262.0; 1 move(s) drove it

The 549 px is the whole of the difference between the two rules on this gesture, and it is
exact rather than a rounding artefact. Neither clamp binds, so

    want - wrong = max * ((py - table_y + grab) - (py - thumb_y)) / h
                 = max * (thumb_y - table_y + grab) / h
                 = 219600 * (12 - 8 + (-3)) / 400
                 = 219600 * 1 / 400 = 549.0

The `1` is the press's own place below the thumb's top (`5`) minus the list's own origin (`8`)
plus the thumb's own place in the window (`12`), and it survives because upstream subtracts
`table_bounds.origin.y` inside `drag_position` (`data_table.rs:332`) and then again in the
percentage (`:356-357`). Reproducing that double subtraction is the point: the port has to land
where upstream lands, not where upstream would have landed if it were tidier.

--------------------------------------------------------------------------------
Why both controls are here
--------------------------------------------------------------------------------
Neither is a second copy of the rule under test. One removes the window-level listener, which is
upstream's own instrument for a scrollbar drag (`tools/upstream/examples/data_table.rs:323`) and
the subject of register row `DD4`. The other replaces the mapping with the one that was actually
there. `tests/evidence/dt2.after.txt` is the green, on all five tiers.
