W6 — editor instances are per (window, key).
Tier: `gos run --main-thread`, and every other tier.

BEFORE THE WORK. Command, against a pristine copy of this project at HEAD
(`git archive HEAD` into /tmp/gpui-before):

    cd /tmp/gpui-before
    timeout -k 5 40 gos run --main-thread tests/gui/w6_editor_per_window.gos

Output: nothing, and exit 124 — the timeout killed it. `gpui::set_text_in` and
`gpui::window_id`, both of which the probe needs to set up its two windows, do
not exist at HEAD. The weak kind of red: an unresolved symbol.

Which is not good enough for this row on its own, because the row is about
*keying* and a registry keyed by `key` alone is not a thing HEAD could express —
HEAD's registry was keyed by `key` alone, but HEAD also had one process-wide
store, so a probe run there would fail for W2's reason and not this row's. So the
check was shown to be sensitive to the mechanism directly, by breaking the
mechanism and watching it fail:

    # EDITORS keyed by the key alone, the window dropped
    - editors.borrow().get(&(win, key.to_string()))
    + editors.borrow().get(&(0, key.to_string()))
    - editors.borrow_mut().insert((win, registered), editor.clone())
    + editors.borrow_mut().insert((0, registered), editor.clone())

    TIER_TIMEOUT=40 gos run --main-thread tests/gui/w6_editor_per_window.gos
    exit=0
    FAIL W6 the child window's editor is not its own: "beta
    line" is where "beta line" belongs

Restored immediately, and the five-tier run below is against the restored tree.
The failure is exactly the shape the row predicts: the child's editor was the
parent's, so the normalisation the child's text needed never happened in the
child's state, and `"beta\nline"` is still sitting there.

**A later run of this probe failed once for a reason that was not the binding.**
The first attempt inside a batch said:

    FAIL W6 the child window's editor is not its own: "beta liney" is where "beta line" belongs

`"beta liney"` — one character appended. The editor takes focus when it is created
and these probes run on a live desktop, so a stray keystroke from whoever is at the
keyboard lands in it. The check was therefore rewritten to name only the two
*wrong* outcomes — the text was never normalised, or the editor took the other
window's text — with the transcript below, and it still catches the break above:

    FAIL W6 the child's editor never normalised its own window's text

That is the third environment trap this project has produced, after the stale build
lock and the window server: see "The probes share the desktop with a human".

This technique — break the mechanism, watch the check fail, restore — is the
answer to a row whose historical red can only be an unresolved symbol, and it is
worth using whenever the capability *is* the reader or the setter. It does not
replace the historical transcript; it supplements it, and both are recorded.

ROUND 84 — the instrument above is retired, and this is why.

The editor under that instrument was a **single-line** editor: it flattened a
break into a space on the way in and stored the result back, and the probe read
that stored-back text. Round 84 made the editor multi-line (`DW1` — the row's own
first clause), which is exactly the behaviour the instrument was measuring: a
multi-line editor keeps its breaks and publishes nothing the program did not
write, so there is no write-back left to observe.

Nothing weaker was available to put in its place. The store read that looked
obvious — `gpui::state_text("note", "")` in the child window — **cannot** answer
this row, and it is worth writing down why, because it is the trap:

    every window has its own store, and the program wrote the child's text into
    the child's store itself. Whether or not any editor adopted it, that store
    holds exactly what the program put there. The two cases are indistinguishable.

What the row is actually about is what the **widget** is holding, and no binding
function could ask. So the round added the reader the row needs:

    gpui::editor_text(key)            // this window's editor, or "" if it draws none
    gpui::editor_text_in(win, key)    // another window's

It is not a test-only hook: `gpui::state_text` answers what the program last
wrote, this answers what the widget holds, and they part company on the question
the row asks — *does this window have an editor on that key at all?* A window
that draws none answers `""` however much text is stored under the key. The
editor leaves its content in a per-`(window, key)` map as it renders
(`editor.rs`: `EDITOR_TEXT`), because a binding function is called between frames
with no `App` and cannot read an entity.

The same break as above, re-run against the new instrument:

    # EDITORS keyed by the key alone, the window dropped
    - editors.borrow().get(&(win, key.to_string()))
    + editors.borrow().get(&(0, key.to_string()))
    - editors.borrow_mut().insert((win, registered), editor.clone())
    + editors.borrow_mut().insert((0, registered), editor.clone())

    DSH_ALLOW_WINDOWS=1 TIER_TIMEOUT=40 ./scripts/tiers.sh tests/gui/w6_editor_per_window.gos run
    === run (interpreter) (exit 0) ===
    FAIL W6 the child window's editor is the first window's editor

Restored immediately. The failure is again exactly the shape the row predicts —
the child window was handed the parent's editor, so the text it is holding is the
parent's — and it no longer depends on a normalisation the widget was never meant
to do.

The probe now names three wrong outcomes: no editor at all in the child window
(`""`), the first window's editor (`"alpha"`), and an editor holding one line
where the child's text has two. The child's text is `"beta\nline"` and the
parent's is `"alpha"`, so the line count separates them and a stray keystroke from
whoever is at the keyboard cannot forge it — which is the environment trap above,
answered rather than merely noted.
