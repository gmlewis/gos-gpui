What changed, all in `gpui-binding/src/`:

  * `style.rs` — `key_context(spec)`, reading the new `ctx=<predicate>` token, plus
    `ctx` in the known-token list so it is not reported as unknown. The value is
    gpui's context-predicate grammar and is passed through rather than validated
    here.
  * `view.rs` — `apply_interactions` applies `.key_context(..)`, and a `ctx=` now
    counts as "this element asks to be interactive", which is what puts it in the
    dispatch tree at all — a context lives on a dispatch-tree node, and a node
    exists only for an element with an id. That is the same rule `hover=` already
    followed.
  * `app.rs` — `keymap_plan` parses the optional `@<context>` and reads it back as
    `"<stroke>:<name>@<context>"`; `bind_keys_spec` splits it out again, validates
    the predicate with `KeyBindingContextPredicate::parse` before handing it to
    `KeyBinding::new` (which `unwrap`s the parse and would otherwise panic the
    window away), and passes it as the binding's context. A predicate gpui cannot
    parse raises `"~keybind.bad|<context>"`.
  * `lib.rs` — `bind_keys`'s doc now promises the `@<context>` grammar, the
    predicate vocabulary, the deeper-match rule and the `~keybind.bad` report;
    `gpui::keymap`'s doc names the contextual read-back. `README.md` documents the
    `ctx=` token beside `hover=`/`active=`/`focus=`.
  * The tests: `tests/km2_key_contexts_test.gos` (five headless cases for the
    grammar) and `tests/gui/km2_key_contexts.gos` (the same stroke gated by a
    context that is present, and a stroke gated by one that is not).

Residual doubt. The context is read from the **focused** node's branch of the
dispatch tree, which is gpui's rule and not this binding's, so the probe focuses by
virtue of the editor taking focus when it is created — a program that moves focus
itself (`focus_next`, a click) moves the context with it, but that is argued from
the dispatch path rather than measured here. The predicate grammar is exercised in
its bare-name form only: `"!Editor"`, `"A && B"` and `"A || B"` are passed through
to gpui's own parser and are not separately probed. And the bindings themselves are
still added to one *application* keymap — KM2 scopes *matching* by context, not by
window, so a stroke bound by window A with a context both windows name will match in
both; routing still sends the event to the window that bound it.
