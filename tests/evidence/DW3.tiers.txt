DW3 — Input widget: real IME and marked text.

THE FIVE TIERS, AND WHICH MACHINE WITNESSED EACH. `DW3`'s probe is
`tests/gui/dw3_input_ime.gos`. Its two running tiers must open a window, and this Mac
may not do that in bulk, so they are measured in the container; the three that compile
are measured headless on the Mac, because the container cannot link a GPUI binary at
all (measured below, not assumed).

    container    check          ok      gos check: exit 0
    container    run            ok      OK DW3 …            (a window, on Xvfb)
    container    run --no-jit   ok      OK DW3 …            (a window, on Xvfb)
    Mac, headless  build        ok      built, NOT run      (compiling opens no window)
    Mac, headless  build --release  ok  built, NOT run

No tier left a process alive, and the two Mac build tiers ran nothing: `gos build`
compiles and links only.

## 1. The container — the two run tiers, and `check`

    ./scripts/gosbox.sh tiers tests/gui/dw3_input_ime.gos

    ok     check: check: ok (1 items typed)
    ok     run: OK DW3 the field inserted at the caret ("ac" then "abc"), cmd-a and backspace cleared it, a composin
    ok     run-nosjit: OK DW3 the field inserted at the caret ("ac" then "abc"), cmd-a and backspace cleared it, a composin
    skip   build: this image cannot link a GPUI binary — no LLVM (`opt`/`llc`) and `tools/` is not staged, so `cc-gpui.sh` is absent; witnessed headless on the Mac instead
    skip   build-release: this image cannot link a GPUI binary — no LLVM (`opt`/`llc`) and `tools/` is not staged, so `cc-gpui.sh` is absent; witnessed headless on the Mac instead
    exit=0

The toolchain this ran against is the pristine one: `/gos` is a clean checkout of
*Towards 0.66.0* (`git status` empty, no `RetainedCallback` anywhere under
`crates/gossamer-binding/src/`), and `/tool/bin/gos --version` answers `gos 0.66.0`.

**Two harness defects were found doing this, and both are fixed rather than worked
around.** `check` used to be reported as `FAIL check: exited 0 — no verdict`, because
this script demanded the running program's `^OK ` of a *compile* tier that has no
verdict line to give (`gos check` answers `check: ok (N items typed)`). It is now judged
by whether it compiled — exit 0 and no `error[`/`FAIL `/panic — which is not weaker: an
error still fails it, and a run tier never reaches that rule. And the two build tiers
are now **skipped by name with their reason** instead of failed, because the failure is
the image's and not the program's. A skip is never counted as a pass, and `exit=0` above
is a pass over the three tiers the container can actually judge.

## 2. Why the container cannot link a GPUI binary — measured

Not inferred from the missing package list. A throwaway container was given `llvm-22`
(the version the toolchain is built against; Debian 12's own apt carries
`1:22.1.8-1~deb12u1`) and the `-dev` libraries a static link wants:

    /usr/lib/llvm-22/bin/opt: Debian LLVM version 22.1.8
    /usr/lib/llvm-22/bin/llc: present
    --- build (debug):
    xkbcommon.…cgu.0:(.text.…<xkbcommon::xkb::State as core::ops::drop::Drop>::drop+0xc):
      undefined reference to `xkb_state_unref'
    collect2: error: ld returned 1 exit status
    error: build: linker failed: cc exited with exit status: 1

So LLVM is the first wall and not the only one: the link then fails on GPUI's Linux
libraries, which `tools/cc-gpui.sh` supplies (`GOS_LINUX_LIBS`) — and `tools/` is
excluded from the staged tree by design, so that wrapper is not in the container. The
container would need **both** LLVM and a staged Linux linker shim; until it has them the
build tiers are not witnessable there, and they are witnessed on the Mac instead.

## 3. The Mac, headless — the three compile tiers

The toolchain is the cached 0.66.0 build of the pristine source
(`~/.cache/learn-gpui/head/bin/gos`, built from the clean `gossamer-head` checkout),
because the `gos` on `PATH` is 0.68.0 and the project pins `gossamer-binding = "0.66.0"`,
so a local run with it stops at cargo's version resolution before it reaches anything.

    export PATH=~/.cache/learn-gpui/head/bin:$PATH
    export GOSSAMER_ROOT=~/.cache/learn-gpui/gossamer-head

    $ gos check tests/gui/dw3_input_ime.gos
    check: ok (1 items typed)
    exit=0

    $ CC=tools/cc-gpui.sh gos build tests/gui/dw3_input_ime.gos
    ld: warning: -multiply_defined is obsolete
    build: 27675512B native executable at target/debug/learn-gpui (target aarch64-apple-darwin)
    exit=0

    $ CC=tools/cc-gpui.sh gos build --release tests/gui/dw3_input_ime.gos
    ld: warning: -multiply_defined is obsolete
    build: 7958296B native executable at target/release/learn-gpui (target aarch64-apple-darwin)
    exit=0

(`ld: warning: duplicate symbol '_gos_rt_concat_init'` lines are elided above; they are
present on every one of these builds and are not new here.)

**What these two tiers do and do not claim.** They claim the program *compiles and
links* under both LLVM backends, which is what a build tier is. They do not claim it
*runs* — running it is the window the container opened, and on this Mac the window is
the thing the owner asked not to have. The register's `DW3` row names the tiers with
that split: run tiers by the container, build tiers by the Mac.
