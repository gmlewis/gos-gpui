`h = 400.0` and `max = 219600.0` are the same in every run, and they are worth a second look:
`400 + 219600 = 220000`, exactly `10_000 * 22.0`, the row count times the row height the port
hands `ui::list`. So `max + h` is the content height — upstream's `scroll_height` — which is the
one quantity in upstream's expression the binding has no name for, and it needs no approximation.

Three things about the green are what make it evidence rather than arithmetic agreeing with
itself, and each is checked by its own line rather than inferred:

  * the move the drag was carried by happened `-150` px from the thumb's bottom edge — that is,
    *outside* the thumb — so the event that moved the list is one the thumb's own hitbox could
    not have delivered. This is the half of the deviation about tracking, and no arithmetic can
    fake it.
  * the list settled at exactly what upstream's mapping asks for, on numbers read off a real
    10 000-row list in a real window: the pointer's own point on the move (`gpui::pointer_xy`),
    the point the press grabbed (from `gpui::element_bounds` and `gpui::scroll_bounds`), the
    viewport and the maximum offset.
  * the rule the example carried before asks for a different place, `549.0` px away, so the
    comparison above is a comparison and not a tautology.
