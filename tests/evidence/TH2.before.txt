TH2 — observe appearance changes while running.

BEFORE THE WORK.

Three transcripts. The first two are the row's absence; the third is the sensitivity of
the check, which matters more here than usual because this row's trigger is outside the
process entirely.

**1. The probe against HEAD's binding.**

    $ timeout -k 5 60 gos run --main-thread tests/gui/th2_appearance_change.gos
    FAIL TH2 the appearance was not changed while the program ran, and nothing arrived
    — the window still reports
    exit 0

Weak for two reasons, and both are recorded rather than tidied away. There is no
`gpui::observe_appearance` at HEAD, so the row's whole mechanism is missing; and the
probe's own "what is the appearance now" — `gpui::appearance()`, which TH1 tested and
which answers `dark` in a plain probe — reads back empty here, because the unbound
call sits in the same frame's callback ahead of it. The unbound call answers a default
and the program runs on, which is the third distinct shape an unbound binding function
has taken in this run (see round 31's note).

**2. The behavioural red: implemented, and nothing provoked.**

`gpui::observe_appearance` in place, the machine's appearance left alone:

    $ timeout -k 5 60 gos run --main-thread tests/gui/th2_appearance_change.gos
    FAIL TH2 the appearance was not changed while the program ran, and nothing arrived
    — the window still reports dark
    exit 0

This is the row stated exactly, and it is also the check's **sensitivity proof**: the
observer is registered and the window's appearance is known, and still nothing arrives,
because gpui does not replay the current value when an observer is registered —
`SubscriberSet::insert`'s `activate` closure is `active.set(true)` and nothing else
(`gpui-0.2.2/src/subscription.rs:88`), so the callback runs only on a real change. A
check that could be satisfied without one would have passed here and proved nothing.

**3. Why the trigger has to come from outside.** gpui 0.2.2 has no public appearance
setter of any kind — `Window::appearance()` reads the platform's `effectiveAppearance`
(`platform/mac/window.rs:1048-1052`) and the only appearance methods on `PlatformWindow`
are the getter, `set_background_appearance` (the blur/opacity setting, unrelated) and
the observer registration; `Window::platform_window` is `pub(crate)`. The platform
delivers the change from the view's own `viewDidChangeEffectiveAppearance`
(`platform/mac/window.rs:2328-2335`), which fires when the system appearance changes.
So a program cannot provoke this, and neither can a probe; the machine's setting has to
move, and the honest way to move it is `scripts/appearance-toggle.sh`, which restores it
whether the program passes, fails, or is killed.
