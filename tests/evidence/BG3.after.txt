The frozen number differs from run to run — it is where the cancel happened to land — which is
why the assertion is `gone_a == gone_b` and not a value. The duplicate-symbol `ld` warnings on
both builds are the toolchain's and predate this run.

What changed, all in `gpui-binding/src/`:

  * `app.rs` — `task_progress(win, id)` and `PROGRESS_STEP` (50ms); `Request::Task` now starts a
    **second** clock beside the work, which reports until the deadline and stops the moment the
    task is retired, and resets the id's progress to 0 when it starts. The completion path sets
    the progress to exactly 1.0 before leaving the result and raising the event, so "it is 1"
    and "there is a result" are the same moment and a program never has to reconcile them.
  * `lib.rs` — `gpui::task_progress(id)`, and `gpui::task`'s doc naming the `"<id>.progress"`
    events.
  * `README.md` — the `task` row, including the painter seam.

**Two clocks, not one, and that is the honest shape.** The work is a thread that cannot be asked
how far along it is, so progress is a clock beside it rather than something the work reports.
For a sleep — which is the only job the binding has — the two are the same thing; for any job
that could report its own progress, this is where that number would go instead. The reporter is
also what makes cancellation visible: it checks the generation on every step, so a retired task
stops drawing.

**A check that passed vacuously, caught and fixed in the round.** See `BG3.before.txt`: the first
version cancelled 50ms in, before the cancelled work had reported anything, so the freeze
assertion was true of a job that never started reporting. The fix is a fourth assertion that
fails when there is nothing to freeze, and it is the second time in three rounds that a passing
run has turned out to be proving less than it looked (round 40's `let _ = raw;` was the first).

Residual doubt. **The progress is the progress of the *wait*, not of the work's own steps** —
the binding knows the duration it was asked for and divides, which is exact for a sleep and
would be a lie for a job that finished early or ran long; there is no channel by which a job
could correct it. Fifty milliseconds is a compromise the program cannot change: a job shorter
than that reports nothing and goes straight from 0 to 1, so a fast job shows no bar at all. The
reports are *events* as well as a reader, which means a program that drains its queue sees one
`"<id>.progress"` per fiftieth of a second for the life of the job — a long job in a busy
program puts a lot of entries through the queue, and nothing coalesces them. And the reader
cannot tell "cancelled" from "still going" once the reports stop; the event that never comes is
what says so.
