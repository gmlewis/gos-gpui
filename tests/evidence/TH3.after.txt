**The check is sensitive to the half a historical red cannot reach.** The transcript in
`TH3.before.txt` shows the name was not consulted; it cannot show that the *contrary*
mistake — letting the chosen palette masquerade as the desktop's own appearance — is
caught, because at HEAD there was no palette to masquerade with. So that was broken on
purpose: the frame's recorded appearance taken from the theme instead of from the
window, nothing else changed,

    FAIL TH3 choosing a palette changed what the OS appearance reports: dark then light

which is the third assertion, and the reason `gpui::appearance` is deliberately *not*
rewired by `set_theme`.

The fourth assertion ("a name the binding does not know is refused") has its sensitivity
from the historical transcript rather than a break: at HEAD the name was taken verbatim
and `theme()` answered `"nosuchtheme"`. It is not separately breakable under this
implementation, because recording an unknown name and keeping the palette pinned are
mutually exclusive while both live in one store key — that is recorded here rather than
claimed as proven.

What changed, all in `gpui-binding/src/`:

  * `view.rs` — `theme_choice(win)`, the palette a program asked for, `"system"` by
    default; `begin_frame` replaces the frame's base `Colors` with
    `Colors::light()`/`Colors::dark()` when one is chosen, **before** TH4's per-window
    token overrides are painted on top, so the two compose in the obvious order. The
    mapping lives in one place and `default_color_for` still answers from an explicit
    appearance without consulting the theme, which is what makes the probe's comparison
    an independent one.
  * `app.rs` — `Request::SetTheme { name }`: a known name is recorded and a frame asked
    for; anything else raises `"~theme.bad|<name>"` and leaves the choice standing.
  * `store.rs` — the request.
  * `lib.rs` — `set_theme`'s doc rewritten from "nothing consults it" to what it now
    promises: the three names, that `gpui::appearance` still reports the operating
    system (choosing how to draw is not lying about the desktop), that the platform's
    window chrome is not repainted, the `~theme.bad` refusal, and that the next frame is
    the first that answers from it. `theme()` now reads that choice and defaults to
    `"system"` rather than the old `"dark"`.
  * `scripts/docs.sh` — claim 6 was the *opposite* claim and was rewritten in the same
    round, as the rule requires: it used to assert the doc admitted the name was inert,
    and now asserts the doc names the palette and says the appearance is untouched. It
    passes (6/6).

Residual doubt. The theme chooses the palette a program *reads* — `default_color` and,
through it, any style string the program builds. It does **not** repaint the platform's
own window chrome, because the binding never owned that: unstyled text and the window's
background still come from gpui's `GlobalColors`, installed from the appearance at window
open. Making the theme reach *styles* is TH5's row (`bg=theme:background` or equivalent),
which is the piece that would let a program write `bg=<name>` instead of reading a hex
value first. `set_theme` is also per window and additive to `theme.<field>=`; the
interaction — a theme chosen and then a field overridden — is composed by construction
(base then overrides) and probed in neither direction. And `theme()` reads the recorded
choice, so a program that sets a theme and reads it back in the same frame sees the old
value: the doc says so, but a probe cannot show a contract it is written to obey.

**A defect this round introduced into the harness, and fixed in the same round.** TH2's
probe was added to `tests/gui/` in round 34, and it *cannot* pass under a plain suite
because nothing in-process can provoke an appearance change. `./scripts/probes.sh` therefore
began reporting it as a failure:

    FAIL   th2_appearance_change: failed twice
    probes: 29/31 passed, 1 flaky (passed only on a retry)
    exit 1

Two of those were not code. `th2` is by design, and `km5_observed_keys` — a `tested` row —
passed alone immediately afterwards (`probes: 1/1 passed`), which is the suite degrading
under its own load that this ledger already documents. The suite was given a way to know
the difference: a probe whose acceptance needs something the suite cannot do declares it
in its header with `// needs: <command>`, and is skipped with a line that names the
command rather than counted as a failure. `scripts/probes.sh` was changed to read it, the
TH2 probe's header to carry it, and the skip verified both ways — `skip th2_appearance_change:
needs scripts/appearance-toggle.sh`, while `w3_events` still runs and passes. A suite that
cries wolf is worse than one that does not run a probe, which is the lesson of the build
lock and the locked screen arriving from a third direction.

The first version of that fix then counted the skipped probe as a *pass* — `probes: 31/31
passed` when thirty had run — which is the same sin wearing the other hat, so the summary
was made to subtract it and name it:

    probes: 1/1 passed
    probes: 1 skipped (see the 'skip' lines above for what each one needs)

With the fix in, the whole suite is clean: `probes: 31/31 passed` → after the counter
change, every probe that runs passes and one is named as skipped.
