What changed, all in `gpui-binding/src/`:

  * `app.rs` — `DELAYS: HashMap<(window, id), generation>`, and `delay_pending`.
    `Request::Delay` inserts a fresh generation and spawns one wait; when it wakes it takes
    the entry **only if it is still its own**, and raises only then — a cancel removed the
    entry, or a later `delay` replaced it, and either way the wait must not fire.
    `Request::DelayCancel` drops the entry, which is what takes the delay back: the waiting
    task wakes, finds it gone, and raises nothing. `TICK_GENERATION` is renamed
    `TIMER_GENERATION` and now numbers both, since a repeating timer's loop and a one-shot's
    wait read it back the same way.
  * `store.rs` — `Request::Delay` and `Request::DelayCancel`.
  * `lib.rs` — `gpui::delay`, `gpui::delay_cancel`, `gpui::delay_pending`, each documented.
  * `README.md` — the `gpui::delay` row in the "making things happen" table and in the event
    sources table.

**A one-shot needs no period, which is why this is not BG4 repeated.** A repeating timer has
to know what it is repeating at; a delay fires once and is over, so the registry holds a
generation and nothing else, and *presence* is the whole of what `gpui::delay_pending`
answers. The generation is still load-bearing, for the reschedule: asking again for an id
that is already waiting restarts the wait, and without it the earlier wait would fire on the
old schedule as well.

**The probe runs in about a second**, in four windows of a few hundred milliseconds, for the
reason round 37 recorded: it needs the window to go on being painted for as long as it runs,
and that is the one thing a probe cannot control here. The margins are the same shape as
BG4's — each assertion is a state that is either true or not, and the only timing relation is
that a 120ms delay falls inside a 320ms window.

Residual doubt. **Restarting a pending delay is implemented and not probed**: the row names a
delay and a cancel, and a third assertion would have cost another window without adding to
what the row asks for, so it is named here instead. A cancelled delay's task still sleeps
until its time comes and then does nothing, so a program that cancels thousands of delays
holds thousands of sleeping tasks briefly — each ends at its own deadline, and none of them
raises. `gpui::delay` floors its period at 1ms, like `gpui::tick`. And the same wall-clock
caveat as BG4: on a machine slow enough to compress the whole probe, an assertion could fail
rather than hang, which is named rather than left to be discovered.
