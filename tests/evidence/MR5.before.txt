MR5 — focus: a `focusable`-only element must be visible to `is_focused`, and the tokens must work on a button.

BEFORE THE WORK. **A red I watched fail, three windows and a rewritten probe later** — and the route to it
is worth reading, because two of my own conclusions were wrong on the way.

The change under test: the style token `focusable` used to be applied as gpui's own `.focusable()`, which
sets a flag and leaves gpui to make a focus handle **inside itself** — one `gpui::is_focused` cannot see,
because it reads back the handles *this* crate keeps. The fix tracks a handle of our own as well.

With that fix reverted, the probe's decisive step fails:

    $ # view.rs: "focusable" => el.focusable()   (MR5's fix reverted)
    $ DSH_ALLOW_WINDOWS=1 ./scripts/run-once.sh tests/gui/mr5_focus.gos 45
    MR5 after 7 focus_next: "" holds focus
    MR5 after 8 focus_next: "" holds focus
    MR5 after gpui::focus("mr5.a"): gpui::focused() says ""
    FAIL MR5 gpui::focus() did not put focus on the button either — the fault is in the handle, not the tab order

`gpui::focus("mr5.a")` asks this crate to focus the handle it keeps under that id. With the fix reverted
there is no such handle at all, so nothing is focused and `is_focused` has nothing to report — which is
exactly the row's complaint, made visible.

**Wrong conclusion 1.** Round 65 "audited" the change against `elements/div.rs:1584` and concluded it had not
regressed anything, and then *removed* `.focusable()` from the arm on the grounds that upstream's
`focusable()` sets only the flag. Round 69 read div.rs:616-620 instead:

    fn track_focus(mut self, focus_handle: &FocusHandle) -> Self {
        self.interactivity().focusable = true;                      // the flag, set here
        self.interactivity().tracked_focus_handle = Some(focus_handle.clone());
        self
    }

`track_focus` sets the flag itself. So the round-65 removal never removed anything, the round-69 restoration
never restored anything, and the flag was never the cause of the failure the probe was showing. Two rounds
spent on a detail that could not matter — the cost of reasoning about an instrument instead of running it.

**Wrong conclusion 2, and this one was in a finding.** Round 69's probe reported that eight `focus_next`
presses moved focus to "nothing", and the ledger read that as the tab order being empty *including* an
element called `~root`. But `~root` only has a handle when a program calls `gpui::on_keys`, which that probe
does not — so the check was vacuous, and "nothing" only meant "nothing this probe knew how to name". Two
other probes (`km4_keys_focus`, `w7_frame_and_keys`) assert `is_focused("~root")` is *true*, which is what
made the over-claim visible.

**What is actually broken is separate from this row**, and the probe now splits the two: `gpui::focus_next`
reaches no element at all, in any of eleven presses across two runs, while `gpui::focus` — the direct route —
works as soon as MR5's fix is in. The tab order is a defect in its own right and belongs to no row of this
register.
