TM2 — select a font family, a rem size and a line height.
Tier: `gos run --main-thread`, and every other tier.

BEFORE THE WORK. Command, against a pristine copy of this project at HEAD
(`git archive HEAD` into /tmp/gpui-before), the runner build lock cleared first:

    cd /tmp/gpui-before
    timeout -k 5 30 gos run --main-thread tests/gui/tm2_font_family.gos

Output: nothing on stdout or stderr, exit 124 — the timeout killed it. Same shape
as TM1's: the probe's first call is `gpui::font_families` on frame 2, above the
`gpui::animate()` that would ask for the next frame.

What the source said: `style.rs`'s `font=` arm was a `match` over seven ramp names
and nothing else —

    "font" => match v { "xs" => el.text_xs(), … _ => el.text_base() }

— so `font=Menlo` silently meant "base size", and there was no token, function or
argument anywhere in the binding that named a font family. `Window::rem_size` had
no setter exposed either, so the ramp was frozen at the platform default.

**This row took three attempts, and the first two are worth recording.**

*The first run of the probe failed* — `FAIL TM2 "W" advances 15.171875 in Menlo
and "i" 3.640625: not monospaced, so it was not selected`. That is what a check is
for: `view.rs`'s `text_metrics` parsed `fs`, `weight`, `bold`, `semibold` and
`italic`, and had no `font` arm at all, so a *measurement* could not select a
family even once the element path could.

*The second showed the element path's comma was worse than missing.* With the
family-resolution added, the probe used `font=Menlo,fs=20` — reading the comma as
a separator between tokens. It is not: after a comma the tail is the **size**, so
`fs=20` was parsed as a family name and silently replaced `Menlo`, measuring a
little differently and no better. Both paths now agree that a comma separates a
family from a size and nothing else, and that a tail which is neither keeps the
family and takes no size.

*The deliberate break missed the first time, and that matters.* Removing the
family assignment from the comma branch changed nothing the probe could see,
because the probe writes `font=Menlo fs=20` — two tokens, which take the
no-comma path. Removing the assignment from *that* branch produced the failure
below. A check that passes under a deliberate break is a signal, and the signal
was about the break, not the check — which is the rule stated in "The
deliberate-break rule"; this is the first time it was tested in practice.

    BREAK — a measurement does not take the family it names
    exit=0
    FAIL TM2 "W" advances 18.96484375 in Menlo and "i" 4.55078125: not monospaced, so not selected

Those two numbers are the default font's: `18.96484375` and `4.55078125` are
exactly TM1's `W` and `i`. So the break made `font=Menlo` measure in the font it
was supposed to replace, which is precisely the failure the probe exists to catch.
Restored immediately; the five-tier transcript below is against the restored tree.
