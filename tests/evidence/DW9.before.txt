DW9 — the observable-state shim: `emit` and `subscribe` over the per-window store.

BEFORE THE WORK.

**Half of this row was already there, and the round says so first.** Upstream's `12_ownership_post`
is `cx.emit` and `cx.subscribe` over an entity graph this binding does not have. `gpui::emit` —
"raise an event from inside a frame, as `"<id>|<payload>"`" — has existed since the early rounds,
documented in its own doc as the `cx.emit` equivalent, and `examples/12_ownership_post.gos` uses it.
What was missing is the other half: a way for a program to say **who is interested**, and for one
signal to reach all of them. That is `subscribe`, and it is a registry and a queue.

**The red is an unresolved symbol, and only that** — the row's half is new surface:

    $ env -u GOSSAMER_IN_RUNNER gos test tests
      FAIL a_subscriber_hears_its_topic: error[GX0002]: name `gpui::emit_in` is not bound in this scope
      FAIL two_subscribers_both_hear_it: error[GX0002]: name `gpui::subscribe_in` is not bound in this scope
      ... and the same for the four cases that follow
    test: 233 passed, 6 failed, 836 assertion(s)

So the sensitivity is the breaks, and there are three, one per claim the row makes.

**`emit` was already taken, and that is a naming decision worth recording.** The first version of
the fan-out was called `emit` too, and the build refused it: `error[E0428]: the name emit is defined
multiple times`. Rather than replace the existing `emit` — which examples use, and which means
"raise one event for an id I name" — the fan-out became **`publish`**, which pairs with `subscribe`
and leaves `emit` as the direct raise. Two shapes of the same thing, named apart on purpose: a
program that knows its listener's id calls `emit`; one that does not publishes to a topic.

**Three breaks**, each applied alone and each caught:

  * **the topic ignored** — every subscriber in the window hears it:

        FAIL a_subscriber_of_another_topic_hears_nothing: panic: no listener for quit

  * **subscribing twice subscribing twice**:

        FAIL subscribing_twice_is_subscribing_once: panic: and the second is not

  * **the roster keyed by topic alone**, so one window sees another's subscriptions:

        FAIL a_subscriber_hears_its_topic: panic: and now one subscriber hears it
        FAIL two_subscribers_both_hear_it: panic: both hear it

    The third is caught, but by the tests that run *first* rather than by
    `a_subscription_belongs_to_one_window`, which was written for it — tests share a process, so a
    roster that ignores the window collides with whatever ran before. Recorded because a break
    caught by the wrong test still leaves the test it was aimed at unproven, and the ordering is not
    something this suite controls.
