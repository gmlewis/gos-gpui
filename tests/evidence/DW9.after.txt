**A subscriber is an event id, not a callback**, and that is the whole design. Upstream's
`cx.subscribe` holds a closure to invoke; a Gossamer program rebuilds its tree every frame, so a
retained closure would be a second copy of the program held by the binding for the life of the app.
An id costs nothing, arrives in the same queue as every other event, and means the program reads a
topic exactly where it reads a keystroke or a menu item.

Residual doubt. **Nothing in `examples/` uses `subscribe` or `publish` yet.** The port of
`12_ownership_post` — the example this row exists for — still approximates its subscriber with an
`if` branch, which its own header says ("the subscriber is an `if` branch", "The port's
'subscriber' runs inside the emitter's own frame callback"). Rewriting it to subscribe and publish
is a faithfulness improvement and would exercise the new surface, and it is **deliberately not
done in this round**: an example's behaviour cannot be verified while windows are forbidden, and
the run's rule is that a change which might break a ported example must be seen not to. It is named
here for whoever can run one again. Also unexercised: a subscription made from *inside a frame by
the current window* (every case here names its window by hand), and `take_events_in` outside a
test. And a topic that raises an event every frame for every subscriber puts one entry per
subscriber per frame through the queue, which a program has to drain — nothing coalesces them.
