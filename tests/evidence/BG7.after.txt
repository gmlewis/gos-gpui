**What is verified, as a fact rather than a guess.** A program with no window can:

  * `fs::write(path, bytes)` — and it *truncates*, so a second write replaces rather than
    appends, which is what saving a file depends on;
  * `fs::read_to_string(path)` and `fs::read(path)`, reading back byte for byte;
  * `fs::exists(path)`;
  * `fs::create_dir_all(path)`, `fs::create_dir`, `fs::read_dir(path)`;
  * `fs::remove_file`, `fs::remove_dir`, `fs::remove_dir_all`;
  * `fs::copy`, `fs::rename`, `fs::canonicalize`, `fs::metadata`;
  * `thread::num_cpus()`.

`"a string".as_bytes()` is how a program gets bytes, and `fs::current_dir` and
`fs::remove_all` are the two names that exist on the Rust side and are not bound.

**What is not: threads, and it is unreachable rather than unbuilt.**

    $ gos check <a program calling thread::spawn>
    error[GR0001]: cannot find `thread::spawn` in this scope
    error[GR0001]: cannot find `thread::join` in this scope

Both exist in `gossamer-std`'s own manifest — `crates/gossamer-std/src/thread.rs:16` is
`pub fn spawn<F, T>(f: F) -> JoinHandle<T>` and `:42` is `pub fn join<T: Debug>(...)` —
and neither is in the language's scope. That is a **toolchain** gap: closing it is a
change to the Gosamer stdlib manifest, not to this binding, and the register's own rule
for that case is to record it and move on rather than stall.

The substitute, and it is a good one: `gpui::task(id, ms)` runs work on GPUI's background
executor, off the UI thread, and reports back through the event queue — row **BG1**. A
program that needs concurrency alongside a window has that; what it does not have is
`std::thread` next to it.
