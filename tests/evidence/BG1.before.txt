BG1 — hand work to a background task, and read its result.

BEFORE THE WORK.

Two reds, and then the row's premise turning out to be mostly stale — which is worth saying
first, because it decided what this round did.

**The premise, read before building to it.** The register says `gpui::task` "spawns a canned
`thread::sleep`" and marks the capability absent. That is half true. The handoff exists and is
not canned in the way that matters: `app.rs` asks GPUI's **background executor** for the work
(`cx.background_executor().spawn(...)`), awaits it, and then re-enters the UI thread to leave
the result and raise the event. What is canned is *the job* — a sleep — and what is missing is
the word **arbitrary**: the work can never be the program's own code. Round 40 checked the
reachable half and recorded the unreachable word; `## Unreachable` carries the compiler's own
answer.

**1. The reading half, against HEAD's binding.**

`gpui::task_result` did not exist, so the convention `"<id>.result"` was written out by hand
wherever a program wanted it — `examples/08_image_loading.gos` does it three times:

    $ env -u GOSSAMER_IN_RUNNER gos test tests
      FAIL the_result_of_a_finished_task_reads_back: error[GX0002]: name `gpui::task_result` is
        not bound in this scope
      ... and the same for the other two cases
    test: 179 passed, 3 failed, 647 assertion(s), 0 ignored, 0 skipped, 0 doc-test(s)

**2. The window half.**

    $ timeout -k 5 40 gos run --main-thread tests/gui/bg1_background.gos
    exit 124, no output

The callback is abandoned at the unbound reader and the window idles.

**3. Three breaks, one per assertion**, because the mechanism's *work* was already there and
the historical red can therefore say nothing about it. Each was applied alone:

  * **the UI thread** — the work done on this thread instead of the background executor's:

        FAIL BG1 the window painted 2 frames while 250ms of work ran, so the work was on the
        UI thread and blocked it

  * **the duration** — work that ignores its `ms`:

        FAIL BG1 the work reported back after 0.085201333s, sooner than the 250ms it was
        asked for

  * **the result** — work that finishes and leaves nothing:

        FAIL BG1 the work finished and left no result to read

**The order of the verdict chain was chosen for these breaks, and the first attempt was
wrong.** The probe originally checked "the result is not readable a third of the way in"
first — and the *blocking* break tripped that instead, because a frozen window does not run
the program again until the work is already over. A failure with the wrong message is a
failure that proves the wrong thing, so that assertion was dropped and the remaining three
were ordered so that each break reaches its own. The frame count is the one the row is really
about: `app.rs`'s comment on that arm claims "the UI thread is free to keep painting while
this runs", and until this probe nothing had ever measured it.
