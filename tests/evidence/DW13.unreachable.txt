DW13 — accessibility semantics registry (roles, labels, AT-SPI/UIA tree): UNREACHABLE.

The register asked for this to be *proved* rather than assumed, with a grep and no
matches. Run against the pinned crate, gpui 0.2.2:

    $ grep -rn "accesskit\|AccessibilityRole\|AccessibilityTree\|AXUIElement\|atspi\|NSAccessibility" \
        ~/.cargo/registry/src/*/gpui-0.2.2/src
    (no output)

    $ grep -n "accesskit" ~/.cargo/registry/src/*/gpui-0.2.2/Cargo.toml
    (no output)

Not "not wired up here" — **not there at all**. gpui 0.2.2 has no accessibility model of
any kind: no `accesskit` dependency, no role or label type, no AX/AT-SPI/UIA call, and
nothing on `Div`, `InteractiveElement` or `Window` that takes a label, a role or a
relationship. Every element this binding builds is an anonymous `div()`
(`gpui-binding/src/view.rs`), and there is nothing to hang a role on.

It is also not a gap a Rust widget can close, which is what makes this row terminal
rather than a route-D row: a widget lives *inside* the binding and draws through
`canvas`, and a canvas has nothing to declare either. A semantics tree needs an API that
takes semantics; there is none to call.

The toolchain change that would close it: an accessibility backend in gpui (`accesskit`
is what the ecosystem uses) exposing roles and labels on elements, at which point this
becomes a route-B token language like `title=` — a `role=` and a `label=` per element,
feeding a tree the binding already walks.

Not the same thing, and worth not confusing with it: **keyboard** access is present and
reachable — focus order, `tabindex=`, `tabstop`, `focus_next()` — and VoiceOver can drive
a window through the standard focus system. That is not a semantics registry and does not
close this row; a screen reader reads "button" from the semantics tree, not from the fact
that something is focusable.
