DW11 — after: the row's three clauses, on every tier.

Two probes, because the row asks three things and they are answered in two different
windows. `tests/gui/dw11_measured_text.gos` is the box and the run: a `w=auto` box is its
content plus its padding, and a run of text can be measured and hit-tested. It is built on
**every** pass, before any check, so the readings it waits on are always there:

    $ ./scripts/gosbox.sh tiers tests/gui/dw11_measured_text.gos
    ok     check: check: ok (6 items typed)
    ok     run: OK DW11 `w=auto` boxes are their content plus their padding (Hello -> 55, HelloHello -> 94, no padding -> 39), gpui::text_width predicts the laid-out run (38.816001892089844 against 39), and offset and pixel round-trip through each other across it (character 3 at 25.00800132751465, marker read back as 3)
    ok     run-nosjit: OK DW11 `w=auto` boxes are their content plus their padding (Hello -> 55, HelloHello -> 94, no padding -> 39), gpui::text_width predicts the laid-out run (38.816001892089844 against 39), and offset and pixel round-trip through each other across it (character 3 at 25.00800132751465, marker read back as 3)
    ok     build: build: 84908104B native executable at target/debug/learn-gpui (target aarch64-unknown-linux-gnu)
    ok     build-release: build: 25378264B native executable at target/release/learn-gpui (target aarch64-unknown-linux-gnu)

`Hello -> 55` is `38.816` of laid-out text plus `2 × 8` of padding, and `no padding -> 39`
is the same run with none: three boxes whose widths are read back from the layout, not
predicted. `tests/gui/dw11_tooltip.gos` is the tooltip, and it is driven by a real pointer
posted onto a real window through XTEST — which is why it carries `// container:` and is
skipped by `scripts/probes.sh` on this Mac (`scripts/gosbox.sh probes` does not read that
line, so the bulk pass runs it):

    $ ./scripts/gosbox.sh tiers tests/gui/dw11_tooltip.gos
    ok     check: check: ok (16 items typed)
    ok     run: OK DW11 a tooltip is absent until the pointer rests (0 wide before), then a box of its own content plus its padding (23 + 16 = 39 by 26 + 16 = 42) at the pointer (151.002, 110.002 for a pointer at (150, 109)), with its target still exactly its own text plus padding (60 around 48)
    ok     run-nosjit: OK DW11 a tooltip is absent until the pointer rests (0 wide before), then a box of its own content plus its padding (23 + 16 = 39 by 26 + 16 = 42) at the pointer (151.002, 110.002 for a pointer at (150, 109)), with its target still exactly its own text plus padding (60 around 48)
    ok     build: build: 85163544B native executable at target/debug/learn-gpui (target aarch64-unknown-linux-gnu)
    ok     build-release: build: 25459456B native executable at target/release/learn-gpui (target aarch64-unknown-linux-gnu)

Four things are in that one line, and each of them is a separate way for it to be wrong:
the tooltip is **absent** before the pointer has been near its target (`0 wide before`);
it is its own content plus its own padding, read back (`23 + 16 = 39` wide, `26 + 16 = 42`
tall) — and the run inside it measures the same as the same run anywhere else on the tier;
it is at the pointer plus gpui's one-pixel offset (`151.002, 110.002` for a pointer posted
at `150, 109`); and it is **not a child** of its target, which is the clause a tooltip laid
out beside its siblings would fail — the `w=auto` target is still `60` around text of `48`,
not widened to the tooltip's own width.

**And a fourth reading came free with it, because it had been wrong.** A tooltip is the one
thing gpui draws that the frame did not hand it: the builder runs on gpui's own half-second
clock, in a task, and the view it answers is laid out inside a *later* frame's
`Window::draw` — after `Root::render` and after `view::reset` have emptied the arena that
described it. So the first version of this probe, which kept child handles into that arena
and read them at draw time, printed

    gpui: noted: child handle 4 names no element in this window (window 1 holds 1)

once per frame and drew the tooltip as an empty box in the frame the program quits on.
`with_tooltip` now copies the tooltip's whole subtree out of the frame that described it —
`view.rs::capture`, every handle rewritten to name the copy — and `snapshot` reads that copy
while the tooltip is drawn. The note is gone from every tier above, and it is gone because
nothing inside a tooltip is a handle into a frame any more.

--- the two halves that are *not* in this file

`bounds` is what makes a box that listens to nothing readable, and DW11's first clause needs
it; the token, `gpui::text_x_of_index` and `gpui::text_index_at` are the round's binding
work, and `tests/evidence/DW11.before.txt` is the same two probes against 329133c, where all
three are absent. The tooltip's *disappearance* is not checked — gpui hides it in
`prepaint_tooltip`'s `check_visible_and_update` once the pointer leaves, and the binding's
`bounds` registry keeps the last box it saw rather than clearing it, so the absence of a box
is only observable before the first time one is ever painted. That is what the `0 wide
before` above is; the disappearance is not.
