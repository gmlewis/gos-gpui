What changed, all in `gpui-binding/src/`:

  * `text.rs` (new) — `lines_of`, which gives every line's byte range **excluding** its break and
    gives a text ending in a break an empty last line; `boundary`, which snaps an offset down to a
    character; then `lines`, `line_of`, `line_bounds`, `line_move` and `word_at`.
  * `lib.rs` — `text_lines`, `text_line`, `text_line_bounds`, `text_line_move`, `text_word`.
  * `README.md` — a "Lines, carets and words" section with the pattern and the two rules worth
    knowing before using it.
  * `CAPABILITIES.md` — DW1, DW4 and DW5 each gained this test path, the red above, the fix, and a
    sentence in their doubt naming what is now built and what is not. **Their status is untouched:
    `todo`**, because each row's acceptance is the widget.

**Two decisions are in the surface rather than in a comment.** Offsets are **UTF-8 byte offsets**,
matching `gpui::styled_text`'s highlight ranges rather than inventing a second convention — and every
answer is snapped down to a character boundary, so an offset inside a multi-byte character gets a
whole one and one past the end is clamped rather than refused. And a word is a run of letters, digits
and underscores with **everything else not a word**: a double-click on a comma takes the comma, not
the run of punctuation and spaces around it. Both are stated in the readers' own docs and in the
README, because a program has to know them to use the answers.

**The column is the caller's to keep.** `text_line_move` is a pure function and remembers nothing, so
a program that wants a caret to come back to the column it left passes the same number again. That is
a real difference from an editor's own caret, and it is deliberate: a hidden preference would be state
this crate would have to own per (window, key) for no gain, when the program already has the number.

Residual doubt.

  * **The widget half of all three rows is untouched**, and that is most of each row: per-line layout
    through the text system (DW1), turning a point into an offset and the mouse gestures themselves
    (DW4), and the painted gutter, wrap toggle and colours (DW5). No window, so nothing has been seen
    to work.
  * `wrap` is not modelled at all: a wrapped line has no byte range, and nothing here knows where a
    wrap would fall. That is DW1's per-line layout, and it is the reason the gutter clause of DW5
    cannot be finished either.
  * `line_move`'s column is bytes, not characters or pixels. For a proportional font the *visual*
    column is pixels, so a caret moving down a line of wide characters will not keep its visual place
    — TM1's measurement (`text_advance`, `text_em_width`) is what would fix that, and a window.
  * The word rule is one rule: no language-specific word breaking, no handling of combining marks as
    part of a word beyond `is_alphanumeric`, and no "select the word *before* the offset" behaviour
    when the offset sits exactly between two words — the character under the offset decides.
  * Nothing here is cached: each call walks the text. A program asking for a line bound per row of a
    thousand-row list walks a thousand times a frame. For the sizes a Gossamer program holds that is
    cheap, and a line index would be the next thing rather than this thing.
