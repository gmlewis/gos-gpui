CL9 — a program-facing clipboard, read/write, text and image.
Tier: `gos run --main-thread`, and every other tier.

BEFORE THE WORK. Command, against a pristine copy of this project at HEAD
(`git archive HEAD` into /tmp/gpui-before), the runner build lock cleared first:

    cd /tmp/gpui-before
    timeout -k 5 60 gos run --main-thread tests/gui/cl9_clipboard.gos

Output: nothing on stdout or stderr, exit 124 — the timeout killed it. Neither
`gpui::clipboard_text` nor `gpui::set_clipboard_text` exists at HEAD, so the probe's
first call is unbound and the callback is abandoned above the `gpui::animate()` that
would ask for the next frame. The weak kind of red.

What the source said: `App::read_from_clipboard` and `App::write_to_clipboard` existed
at HEAD (`gpui-0.2.2/src/app.rs:1053,1041`) and were reached in exactly one place,
`editor.rs`'s cut/copy/paste, where a `Context<Self>` was in hand. A binding function
has no `App`, so a program could not reach either — the same plumbing gap as the
text system, with the same two answers: read once per frame in `begin_frame`, where
there is a valid `&App`, and write through the request pump, which has one too.

**The break is the interesting part, for two reasons.** Dropping the write:

    BREAK — the write is never made
    exit=0
    FAIL CL9 the clipboard reads back as "<redacted>", not the text written to it

  * It fails for exactly the right reason: with nothing written, the probe read back
    **whatever was already on the user's clipboard** — which is the strongest possible
    demonstration that the reader is really reading the system clipboard and not a
    binding-side cache.
  * The value is **redacted here on purpose.** It was a real URL from the user's
    clipboard, and a test transcript is not the place for it. The probe writes a
    distinctive marker and puts the original back precisely so that running it does
    not leave the author's clipboard in a repository.
