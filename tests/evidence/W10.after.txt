W10 — `close_window()` addressed to a named window.

AFTER THE WORK. Command, in this tree:

    TIER_TIMEOUT=25 ./scripts/tiers.sh tests/gui/w10_close_named_window.gos

Output, identical on all five tiers (`check` prints `check: ok (2 items typed)`;
each of the other four exits 0 with no stderr):

    OK W10 window 2 closed window 3 by name, and window 2 kept going

What the probe does: window 1 opens window 2; window 2 opens window 3; window 2
closes window 3 — by id, `gpui::close_window_in(3)` — at its own frame 3, while
window 3 is animating. Window 1 is the witness: it samples all three windows'
self-reported frame counts at frame 8 and again at frame 12, and requires that
window 3's stopped while window 2's kept climbing. Window 3's absence is only
meaningful because it had reported at least once before it was closed, which
the probe also requires.

The verdict line carries no counters on purpose. The first version printed them
and the two LLVM tiers disagreed by one frame on window 2 — the close lands
between window 3's frames at a point that depends on scheduling, not on the
binding. Tier parity needs one line, so the counters are checked, not printed.

What makes it pass: `store::Request::CloseWindowAt { target }`, raised by
`gpui::close_window_in`, and `app.rs`'s `close_named_window`, which walks
`cx.windows()`, asks each window's root view which id it is (`Root` is the only
root type in this binding, so the downcast always succeeds), and calls
`window.remove_window()` on the match. It runs from a `cx.defer`, never from
inside the frame — see `W10.before.txt` for the panic that taught that.
