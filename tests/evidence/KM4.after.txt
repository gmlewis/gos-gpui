KM4 — `on_keys(true)` must take focus at any frame, not only `frame() <= 2`.

AFTER THE WORK. In this tree:

    TIER_TIMEOUT=45 ./scripts/tiers.sh tests/gui/km4_keys_focus.gos

Output, identical on all five tiers (`check` prints `check: ok (1 items typed)`; each of
the other four exits 0 with no stderr but the toolchain duplicate-symbol link warnings
every build in this project prints):

    OK KM4 the window took focus on frame 20, when the program asked for the keyboard, and still holds it at frame 24

The probe asks for the keyboard at frame 20 — about a third of a second in, and eighteen
frames past the old gate — and reads `gpui::is_focused("~root")` at frame 24. That reader
answers whether the window's own focus handle is the focused one, so the check is of the
real focus state rather than of a flag the binding could set and forget.

What is new, in `gpui-binding/src/view.rs`:

  * `KEYS_ARMED`, a per-window set of the windows whose keyboard the root has already
    taken focus for. "The frame the program enabled it" is not a frame number — it is
    the transition into this set, which is what makes the behaviour the same at frame 2
    and at frame 2000.
  * `listen_for_keys` takes focus when the root does not have it and either the window
    is not yet armed or nothing at all is focused, then arms the window.
  * `view::disarm_keys`, called from `gpui::on_keys(false)`, so that turning the keyboard
    off and on again takes focus again.

`gpui::on_keys`'s doc now says all of that, including the part the old text got wrong:
it said the field "takes over until focus comes back to the window", which was true and
useless — focus never came back, because the only frame that could take it had passed.

Not verified here, and in the row's residual doubt: that a focused text field keeps
focus while `on_keys(true)` is on. The mechanism is `window.focused(cx).is_none()` —
the window takes focus only when nothing has it — but `gpui::focus_next()` does not move
focus away from the root even with an editor in the tree, so a probe cannot put focus
somewhere else and watch it stay. The regression suite is the weaker evidence that
nothing broke: `examples/09_input` and every other example with an editor still render
silently.
