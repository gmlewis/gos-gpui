SC4 — scroll handles that survive a rebuild, a tab switch or a list recycle.

AFTER THE WORK. Command, in this tree:

    TIER_TIMEOUT=40 ./scripts/tiers tests/gui/sc4_scroll_survives.gos

Output, identical on all five tiers (`check` prints `check: ok (1 items typed)`;
each of the other four exits 0 with no stderr):

    OK SC4 the offset survived two frames off screen and a tree that renumbered around it

What the probe does, and why "survives a rebuild" needs more than the obvious
version: the element tree is described from scratch *every* frame in this
binding, so surviving one rebuild is the ordinary case and proves nothing. The
probe therefore puts the handle through the two things that actually move an
element out from under state kept beside the tree:

  * **frames 7 and 8 — a tab switch.** The container is not in the described tree
    at all: nothing renders it, nothing lays it out, and nothing clamps its
    offset. `gpui-binding/src/scroll.rs` holds the handle in a thread-local map
    that the frame never touches, so the offset is simply still there at frame 9.
    The probe asserts this directly at frame 8 — reading the offset while the
    container is off screen — rather than only inferring it from frame 12.
  * **frames 10 and 11 — a sibling inserted ahead of the container.** Every
    automatic element id the frame issues after it shifts by one. A handle keyed
    by an automatic id moves with it and is lost; one keyed by the container's own
    `id=` token does not. This is the half that the `id=` token from SC1 is
    load-bearing for.

The offset must read back as -40 after both. The probe also fails early — at
frame 2 — if the container reports nothing to scroll, so a pass cannot come from a
container that never scrolled.
