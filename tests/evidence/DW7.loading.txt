DW7 — the loading subtree, made due. A load that is genuinely still loading at the 200ms mark.

Why this needs its own run. `gpui::image_request`'s loading subtree is due only while the load
is pending *and* `LOADING_DELAY` (200ms, `elements/img.rs:31`) has passed since it started
(`:373-395`). Every file in this repo decodes well inside a frame — including the 4.4MB
`examples/assets/black-cat-typing.gif`, which an earlier revision of the probe pointed this cell
at while it never once saw `loading` — so the bulk pass records that state as never due. The one
source that is a path *and* not instantaneous is a fifo: `fs::read` on it blocks until a writer
arrives (`img.rs:601`), on a background thread (`app.rs:2018`), so the load stays pending while
frames go on.

The run. `./scripts/gosbox.sh shell` is this same environment; this is what it ran. Note the
redirection: `( … ) > /tmp/dw7-slow.pipe` opens the fifo for writing *before* the subshell's
`sleep`, so the open blocks until the app's first render opens the read end, and the second of
silence is then measured from that render rather than from container start. The writer hands the
loader a real PNG, so the load is pending across the 200ms mark and then succeeds — which is also
what lets the process exit at its verdict instead of at a timeout.

The slow cell's whole life is in the states list: `blank` (pending, not yet 200ms) → `loading`
(the subtree, laid out 62px) → `image` (the picture, once the writer answered). The last check is
the one that would catch a decision cached at `loading`: the subtree has to be *given up* when
the load lands, and the state says it was.

What this is not: a photograph. The container cannot carry a client window's pixels into its
framebuffer (`DW3.capture.txt`), so what is checked is which subtree the element chose and that
it laid out, not what it looks like.
