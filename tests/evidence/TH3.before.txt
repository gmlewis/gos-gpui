TH3 — a real theme: `Colors::for_appearance` wired, named colour table, `set_theme`
retired or backed.

BEFORE THE WORK — and the first thing the work was is a correction to this row.

**Two of the row's three clauses were already true, and the round says so instead of
pretending to have built them.** `Colors::for_appearance` has been wired since TM4 —
all eight `Colors` fields cached and chosen by the window's appearance — and TM4's row
records that its own obstacle column ("light defaults only") was already stale when it
was written. The named colour table has been readable since TH1 and TM4:
`gpui::colour_names()` answers the eight names, `gpui::default_color(name)` the window's
value for one, and `gpui::default_color_for(appearance, name)` the other palette's. The
third clause is the whole of the remaining work.

**The third clause, measured.** `set_theme` recorded a name and **nothing consulted it**;
its own doc said so, and `scripts/docs` claim 6 guarded that admission:

    /// Nothing consults it. It has no effect on any colour — `gpui::default_color`
    /// answers the platform's own colours, chosen from the window's appearance —

With the probe in place and nothing else changed, on a dark machine:

    $ timeout -k 5 60 gos run --main-thread tests/gui/th3_theme.gos
    FAIL TH3 the "light" theme's background should be #ffffffff and the table answers
    #222222ff, so the theme name is still not consulted
    exit 0

That is the row's absence exactly: the machine is dark, the program asked for the light
palette, and the named table went on answering the dark one. `#222222ff` is the dark
background and `#ffffffff` the light one, both read through `gpui::default_color_for`,
so the verdict is a comparison between two colours the binding itself publishes rather
than against a constant.

A first draft of the probe put the "a name the binding does not know is refused"
assertion first, and it fired instead — `theme() reads "nosuchtheme"`, because at HEAD
the name was taken verbatim and nothing followed from it. The assertions were reordered
so the row's own sentence fails first; both failures are real and the order is the only
thing that changed. That matters for the sensitivity question below: assertion 4's
historical red is *that* one.

**The mechanism, read from the source before building.** `Colors::for_appearance` takes a
`&Window` and maps its appearance onto `Colors::light()`/`Colors::dark()`
(`gpui-0.2.2/src/colors.rs:36-41`); the binding's `begin_frame` clones the window's global
`Colors` and paints TH4's per-window overrides onto it. So a theme is a choice of *base
palette*, which is why `set_theme` is a request that asks for a frame: the base is read at
the start of a frame, before the view callback that could set it.
