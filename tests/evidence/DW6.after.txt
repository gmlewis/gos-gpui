DW6 — queued prompts.

AFTER THE WORK. Headless, and the queue is the whole of what a check can reach.

    $ ./scripts/tiers tests/dw6_prompts_test.gos check

The check tier prints nothing but that line: six lints the file had raised — discarded tail values —
were corrected rather than tolerated.

What changed, all in `gpui-binding/src/`:

  * `prompts.rs` (new) — one FIFO queue of `Prompt`s per window, `NEXT_ID` counting up so a late
    answer names a prompt that is gone rather than a different one that took its number, and
    `ask_in`, `head_in`, `answer_in` (which refuses anything but the head, and any button that names
    no button), `cancel_in`, `queue_in`, `clear_in`, plus `describe` and `listed` for the two ways a
    program reads them.
  * `lib.rs` — `prompt`, `prompt_current`, `prompt_buttons`, `prompt_answer`, `prompt_cancel`,
    `prompts`, `prompts_clear`, and the `_in` twins of the four that a `gos test` needs to name a
    window by hand. `prompt_answer` raises `"prompt|<id>|<button>"` from the answered prompt's window.
  * `README.md` — an "Answers to questions" section with the once-a-frame loop written out, since the
    program is the renderer.

**The program is the renderer, and that is a decision rather than a gap.** A Gossamer program rebuilds
its tree every frame; a dialog drawn from the same tree is an element like any other, is styleable
with the same language, and can be answered through the queue. The *native* dialog — `Window::prompt`,
awaiting its receiver in a task and answering with the index that comes back — is the other consumer
of the same queue, **and it is not implemented**. The reason is in the register row and repeated here
because it is the round's chief judgement: it cannot be observed without a window, this run may not
open one, and the queue already lets a program ask and be answered. Building it would add a path that
no check in this run could reach, which is the thing this run's rules exist to prevent.

Residual doubt.

  * **No dialog has ever been drawn.** The queue's behaviour is checked; the *dialog* — the loop in the
    README, the drawing, the click that picks a button — is unobserved, and the native path is not
    written at all. A program that asks is answered; that a person would see the question is not
    verified.
  * Cancelling is allowed for **any** prompt in the queue, not just the head, so a program can drop a
    question that has not come up. That is deliberate — a program that has moved on should not have to
    wait its turn to say never mind — but it does mean `prompt_cancel` can remove something a person
    was about to be shown.
  * Ids are per process, not per window, so they are not small numbers in a long-running program; they
    are never reused, which is the point.
  * Nothing times a prompt out and nothing re-queues one on failure, since there is no failure path
    without the native dialog.
  * `prompts()` reports `"<id>|<title>"` and omits the message, so a listing cannot be echoed into a
    dialog without a second read. That is the shape a list wants; a program wanting the message reads
    the head.
