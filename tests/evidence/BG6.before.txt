BG6 — animation: pause, resume, stop, duration and easing.

BEFORE THE WORK.

Three reds: the two halves of the mechanism, and the three breaks that show which assertion
each half is load-bearing for.

**1. The clock half, against HEAD's binding.**

`gpui::animation`, `gpui::animation_phase` and friends do not exist at HEAD, and an unbound
binding function's failure mode is not a diagnostic:

    $ timeout -k 5 40 gos run --main-thread tests/gui/bg6_animation.gos
    exit 124, no output

What was missing is not a detail. `gpui::animate()` asks for another frame and nothing more;
there was no animation *clock* in the binding at all. A program that wanted something to move
over a known duration read `gpui::now()` itself, subtracted, divided and clamped, and its
"pause" was a flag in its own state. The painters take a `phase` the program computes by hand
(`gpui::draw("bars", phase, …)`), which is exactly the seam this fills.

**2. The curve half.**

    $ env -u GOSSAMER_IN_RUNNER gos test tests
      FAIL the_easings_have_names: error[GX0002]: name `gpui::animation_easings` is not bound in this scope
      ... and the same for `gpui::easing_at` in four more cases
    test: 166 passed, 5 failed, 599 assertion(s), 0 ignored, 0 skipped, 0 doc-test(s),
    across 51 file(s), 35 with no tests

**3. The three halves of the clock, by deliberate break**, each applied alone. The row names
four things — pause, resume, stop, and a duration — and the probe asserts each separately, so
each break has to fail *its own* assertion:

  * **pause**, by letting the clock run while "held":

        FAIL BG6 a paused animation reports itself as "running"

  * **resume**, by restarting the animation rather than carrying it on:

        FAIL BG6 a tenth of a second after resuming, the phase is 0.32886930333333336: resuming restarted the animation instead of carrying it on

  * **stop**, by accepting the request and doing nothing:

        FAIL BG6 a stopped animation reports itself as "done"

The resume break is the one that earned its own assertion. The first version of the probe only
sampled the phase *after* the animation had finished, where a restart and a carry-on look
identical — both read 1.0 — so "resume does not restart" was unprovable. A tenth of a second
after the resume, a carry-on is at four fifths and a restart is at a tenth; the assertion
was added, and this break is what shows it is load-bearing.

**The first break of the retake was wrong, and it is worth recording why.** Its edit dropped
the line that sets `running_since`, so the animation never resumed at all and the phase read
`0` — a failure, but not the failure the message named. The break was applied again properly
(the clock restarting *and* running), which is where `0.32886930333333336` comes from. A break
that fails for the wrong reason proves the wrong thing.
